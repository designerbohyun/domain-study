    6회차 · Bandwidth, Latency, Coalesced Access, Unified·Pinned Memory

    지난 5회차에서는 GPU 메모리의 칸들, 즉 레지스터, Shared Memory, L1과 L2 캐시, VRAM을 봤습니다. 오늘은 그 칸들 사이를 데이터가 얼마나 많이, 얼마나 빨리 오가는지 보겠습니다.

    메모리 성능은 두 숫자로 봅니다. 1초에 얼마나 많이 옮기느냐가 이고, 요청한 뒤 첫 데이터가 올 때까지 얼마나 걸리느냐가 입니다. 그리고 이 두 숫자를 실제로 잘 쓰는 방법이 두 가지 있습니다. GPU 안에서는 병합 접근, CPU와 GPU 사이에서는 Pinned Memory와 Unified Memory입니다.

    PART 1

    Bandwidth (대역폭)

    먼저 "얼마나 많이"부터 보겠습니다.

    1.1

    정의

    은 1초에 옮길 수 있는 데이터의 양입니다. 단위는 GB/s, TB/s를 씁니다.

    • 스펙에 적힌 이론 최대치, 즉 peak와 실제로 나온 값, 즉 achieved를 구분합니다.
    • 메모리 대역폭은 길의 개수, 즉 버스 폭에 길 하나의 속도를 곱하고 8로 나눈 값입니다. 5회차 1.4에서 계산해 본 식입니다.
    • H100 SXM의 HBM3 대역폭은 3.35TB/s입니다.
    1.2

    등장 배경

    • GPU의 연산 성능은 세대마다 몇 배씩 늘었는데, 메모리 대역폭은 그보다 느리게 늘었습니다. 1995년에 이 현상을 이라고 부르기 시작했습니다.
    • 그러자 같은 GPU에서도 어떤 작업은 빠르고 어떤 작업은 느렸습니다. 연산에 막혔는지, 메모리에 막혔는지 가릴 기준이 필요했습니다.
    "그럼 연산량과 데이터 양의 비율로, 어디에 막혔는지 그림 한 장으로 보자!"그래서 등장한 것이 바로 입니다.
    • 2009년 버클리의 Williams, Waterman, Patterson이 발표했습니다.
    • 이때부터 대역폭은 성능을 판단하는 핵심 지표가 됐습니다.
    1.3

    구조

    1. 산술 강도

    • , 영어로 Arithmetic Intensity는 연산량을 메모리에서 옮긴 바이트 수로 나눈 값입니다. 단위는 FLOP/Byte입니다.
    • 한 번 읽은 데이터로 계산을 많이 할수록 산술 강도가 높습니다.

    2. Roofline 모델

    구성하는 일H100 SXM 수치
    연산 지붕연산 성능의 상한BF16 dense 989 TFLOPS
    메모리 경사대역폭 곱하기 산술 강도만큼만 성능이 나옴3.35TB/s
    꺾이는 지점두 선이 만나는 산술 강도약 295 FLOP/Byte
    • 성능의 상한은 연산 지붕과 메모리 경사 중 낮은 쪽입니다.
    • 989 TFLOPS를 3.35TB/s로 나누면 약 295입니다. 산술 강도가 이보다 낮은 작업은 메모리에 막힙니다. 이걸 라고 합니다.

    3. 계층마다 다른 대역폭

    • 레지스터가 가장 넓고, 그다음이 Shared Memory, L2, HBM 순입니다.
    • GPU 밖으로 나가면 NVLink, PCIe, 네트워크 순으로 좁아집니다. 7회차부터 차례로 다룹니다.
    1.4

    작동 방식

    LLM이 토큰을 하나씩 만드는 단계, 즉 로 따라가 보겠습니다.

    1. 가중치 읽기: 토큰 하나를 만들 때마다 모델 가중치 전체를 VRAM에서 한 번 읽습니다.
    2. 상한 정하기: 배치가 1이면, 대역폭 나누기 모델 크기가 1초에 만들 수 있는 토큰 수의 상한입니다.
    3. 계산해 보기: 7B 모델을 FP16으로 두면 14GB입니다. 3.35TB/s를 14GB로 나누면, 1초에 약 240토큰이 이론 상한입니다.
    4. 배치 키우기: 한 번 읽은 가중치로 여러 요청을 함께 계산하면 산술 강도가 올라가, 메모리 바운드에서 벗어납니다.

    반대로 학습이나 긴 프롬프트를 한 번에 읽는 prefill 단계는 큰 행렬 곱셈이라 산술 강도가 높습니다. 이때는 Tensor Core 성능이 상한입니다.

    Q. 13B 모델이면 토큰 속도 상한은 얼마인가요?

    FP16으로 26GB입니다. 26GB를 3.35TB/s로 읽는 데 약 7.8ms가 걸리니, 1초에 약 130토큰이 이론 상한입니다. 모델이 두 배 크면 속도는 절반입니다.

    Q. 우리 작업이 메모리 바운드인지 어떻게 아나요?

    Nsight Compute의 Roofline이나 Speed of Light 항목에서 메모리 처리량 비율과 연산 처리량 비율을 비교합니다. 운영 쪽에서는 DCGM의 DRAM Active가 높고 Tensor Active가 낮으면 메모리 바운드일 가능성이 큽니다. DCGM은 23회차에서 다룹니다.

    1.5

    이점

    대역폭이 클수록 얻는 것입니다.

    • LLM 추론이 빨라집니다: decode는 대역폭에 묶여 있어서, 대역폭이 곧 토큰 속도입니다.
    • 같은 칩도 빨라집니다: H200은 H100과 계산 칩이 같고 대역폭만 4.8TB/s로 늘렸는데, LLM 추론이 크게 빨라졌습니다. 5회차 1.5에서 본 사례입니다.
    • 작은 에서도 GPU를 덜 놀립니다: 배치를 크게 키우지 못하는 대화형 서비스에서 특히 효과가 큽니다.
    1.6

    부재 시 문제

    대역폭이 모자란다고 가정해 보면, 이런 문제가 생깁니다.

    • 연산 유닛이 데이터를 기다리며 놀아서, 스펙에 적힌 의 일부만 씁니다.
    • 더 좋은 GPU로 바꿔도 배치를 키우지 않으면 체감 개선이 작습니다. 연산 성능만 늘고 대역폭은 덜 늘었기 때문입니다.
    1.7

    단점

    대역폭이라는 지표와 하드웨어의 한계입니다.

    • 이론치에 닿지 못합니다: 실제로 측정하면 은 보통 이론치의 80~90%대가 나옵니다.
    • 대역폭만으로는 성능을 설명하지 못합니다: 지연, 접근 패턴, 캐시 적중률도 함께 영향을 줍니다. PART 2와 PART 3에서 봅니다.
    • 비쌉니다: 대역폭을 늘리려면 HBM을 더 쓰거나 더 빠른 세대로 바꿔야 해서, 가격과 전력이 함께 오릅니다. 5회차 1.7에서 봤습니다.
    1.8

    단점 극복을 위한 대안 기술

    1.

    • 뜻: 숫자를 더 적은 비트로 저장해, 읽어야 할 바이트 자체를 줄입니다. 4회차에서 봤습니다.
    • 해결하는 단점: 대역폭이 그대로여도 1초에 만드는 토큰 수가 늘어납니다.

    2. 배칭

    • 뜻: 한 번 읽은 가중치로 여러 요청을 함께 계산합니다. 요청이 들어오는 대로 묶는 Continuous Batching은 20회차에서 다룹니다.
    • 해결하는 단점: 산술 강도를 높여 메모리 바운드에서 벗어납니다.

    3. 타일링과 커널 퓨전

    • 뜻: 데이터를 Shared Memory나 캐시에 두고 여러 번 쓰고, 여러 단계를 한 커널로 합쳐 중간 결과를 VRAM에 쓰지 않습니다. 5회차 PART 2에서 봤습니다.
    • 해결하는 단점: VRAM 왕복 자체를 줄입니다.

    4. 여러 GPU로 대역폭 합치기

    • 뜻: 모델을 여러 GPU에 나눠 담으면, 각 GPU가 자기 몫만 읽습니다. Tensor Parallelism은 17회차에서 다룹니다.
    • 해결하는 단점: GPU 한 장의 대역폭 한계를 넘습니다. 대신 GPU 사이 통신이 늘어납니다.

    1.10

    최신 트렌드

    1. 연산과 대역폭의 차이가 더 벌어집니다

    • 대역폭은 H100의 3.35TB/s에서 B200의 8TB/s, 2026년 Rubin의 22TB/s로 늘었습니다. 5회차 1.10에서 본 숫자입니다.
    • 그런데 4비트 연산 성능은 이보다 더 빠르게 늘어서, GPU를 다 쓰려면 산술 강도가 더 높아야 합니다.

    2. 단계마다 다른 칩을 씁니다

    • NVIDIA는 2025년 9월 를 발표했습니다. HBM 대신 GDDR7 128GB를 쓰는, prefill 전용 GPU입니다.
    • 연산이 많고 대역폭은 덜 필요한 prefill은 CPX가, 대역폭이 중요한 decode는 HBM을 쓴 Rubin GPU가 맡는 구성입니다.
    • SemiAnalysis는 CPX의 대역폭을 약 2TB/s로 추정했고, GDDR7로 바꿔 GB당 메모리 값을 절반 넘게 줄였다고 분석했습니다.
    꼭 알아 둘 것대역폭은 늘어도 연산보다 느리게 늘어납니다. 그래서 데이터를 덜 읽는 기술과, 단계마다 맞는 메모리를 고르는 설계가 함께 중요해집니다.
    PART 2

    Latency (지연)

    여기까지가 "얼마나 많이"였습니다. 이제 "얼마나 빨리", 즉 지연으로 넘어가겠습니다.

    2.1

    정의

    은 데이터를 요청한 뒤 첫 결과가 올 때까지 걸리는 시간입니다. 단위는 사이클, ns, μs를 씁니다.

    • 대역폭은 양이고, 지연은 시간입니다. 둘은 서로 다른 축입니다.
    • H100에서 HBM을 한 번 읽는 데는 수백 사이클이 걸립니다.
    Q. 대역폭이 크면 지연도 작은 것 아닌가요?

    아닙니다. HBM은 일반 DDR 메모리보다 대역폭이 수십 배 크지만, 한 번 접근하는 지연은 비슷하거나 더 깁니다. 대역폭은 동시에 얼마나 많이, 지연은 하나가 얼마나 빨리입니다. 길이 넓다고 거리가 짧아지지는 않습니다.

    2.2

    등장 배경

    • CPU는 큰 캐시와 분기 예측으로 지연 자체를 줄이는 데 칩 면적을 많이 씁니다.
    • GPU는 수만 개 스레드가 동시에 메모리를 요청합니다. 요청 하나하나의 지연을 CPU처럼 줄이려면 칩 면적이 너무 많이 듭니다.
    "그럼 기다리는 동안 다른 warp를 돌려서, 지연을 줄이지 말고 숨기자!"그래서 GPU가 택한 것이 바로 , 영어로 latency hiding입니다.
    • 2006년 G80부터 warp를 사이클마다 바꿔 실행하는 하드웨어가 들어갔습니다.
    • 2회차에서 본 Occupancy, 즉 점유율이 바로 이 숨기기를 위한 지표입니다.

    2.4

    작동 방식

    지연을 숨기는 원리는 , 영어로 Little's Law로 설명합니다.

    1. 필요한 양 계산하기: 대역폭을 다 쓰려면, 대역폭 곱하기 지연만큼의 데이터가 늘 이동 중이어야 합니다. 3.35TB/s 곱하기 500ns, 약 1.7MB입니다.
    2. 많이 요청하기: 스레드 하나는 몇 바이트씩만 요청하니, 1.7MB를 채우려면 수만 개 스레드가 동시에 요청해야 합니다. GPU가 스레드를 그렇게 많이 쓰는 이유입니다.
    3. 바꿔 실행하기: 메모리를 기다리는 warp는 잠시 두고, 준비된 다른 warp를 바로 실행합니다.
    4. 겹치기: 시스템 수준에서는 스트림과 비동기 복사로, 계산하는 동안 다음 데이터를 옮깁니다.
    2.5

    이점

    지연이 낮거나 잘 숨겨질수록 얻는 것입니다.

    • 응답이 빨라집니다: 작은 작업, 작은 배치에서 응답 속도가 좋아집니다. LLM 대화형 서비스의 체감 속도가 여기서 나옵니다.
    • 동기화 대기가 줄어듭니다: 분산 학습에서 GPU끼리 기다리는 시간이 줄어듭니다. 10회차에서 다룹니다.
    • 을 다 씁니다: 지연을 잘 숨기면, 지연이 길어도 대역폭을 끝까지 씁니다.
    2.6

    부재 시 문제

    지연을 고려하지 않고 짠다고 가정해 보면, 이런 문제가 생깁니다.

    • 동시에 요청하는 스레드가 모자라, 대역폭이 남는데도 느립니다. 이 낮을 때 생기는 일입니다.
    • 작은 커널을 아주 많이 실행하면, 커널을 실행하는 지연이 실제 계산 시간보다 커집니다.
    • LLM decode가 실제로 이렇습니다. 배치가 작으면 커널이 짧아 실행 지연이 병목이 되고, 그래서 vLLM과 TensorRT-LLM은 CUDA Graphs를 씁니다.
    2.7

    단점

    지연 자체의 성질에서 오는 한계입니다.

    • 줄이기 어렵습니다: 지연은 물리적 거리와 신호 처리로 정해집니다. 지연은 세대가 바뀌어도 크게 줄지 않습니다.
    • 병렬로 줄지 않습니다: 대역폭은 길을 늘려 키울 수 있지만, 지연은 길을 늘려도 그대로입니다.
    • 숨기는 데도 자원이 듭니다: 많은 warp를 올리려면 레지스터와 Shared Memory를 나눠 써야 합니다. 5회차 3.7에서 봤습니다.
    2.8

    단점 극복을 위한 대안 기술

    1. 지연 숨기기

    • 뜻: 점유율을 높이고, 한 스레드 안에서도 서로 상관없는 명령을 이어 실행합니다. 이걸 , 명령 수준 병렬성이라고 합니다. 비동기 복사인 cp.async와 TMA로 다음 데이터를 미리 가져옵니다.
    • 해결하는 단점: 줄일 수 없는 지연을 계산 뒤로 감춥니다.

    2. 지연 피하기

    • 뜻: 자주 쓰는 데이터를 레지스터나 Shared Memory처럼 가까운 계층에 두고, 커널 퓨전으로 VRAM 왕복을 없앱니다.
    • 해결하는 단점: 먼 메모리까지 가는 횟수 자체를 줄입니다.

    3.

    • 뜻: 여러 커널 실행을 그래프 하나로 미리 등록해 두고, 한 번에 실행합니다.
    • 해결하는 단점: 커널마다 붙는 실행 지연을 줄입니다.

    4. 직접 경로

    • 뜻: RDMA는 CPU를 거치지 않고 네트워크 카드와 GPU가 직접 주고받습니다. NVLink는 PCIe보다 짧은 지연으로 GPU끼리 잇습니다. 9회차에서 다룹니다.
    • 해결하는 단점: 시스템 수준의 지연을 줄입니다.
    2.9

    대안과의 비교

    전략방식맞는 작업대표 예

    줄이기 (CPU 방식)캐시와 예측으로 대기 자체를 줄임순차적이고 분기가 많은 작업큰 L3 캐시, 분기 예측

    2.10

    최신 트렌드

    1. 커널을 하나로 합치는 메가커널

    • 2025년 스탠퍼드 Hazy Research는 Llama 1B 모델의 decode 전체를 커널 하나로 합친 을 발표했습니다. 커널 사이의 빈틈, 즉 실행 지연을 없애려는 시도입니다.
    • 2025년 12월에는 CMU 연구진이 모델을 메가커널로 자동 변환하는 컴파일러 MPK, Mirage Persistent Kernel을 공개했습니다. CUDA Graphs는 모양이 바뀌면 다시 만들어야 한다는 한계를 넘으려는 접근입니다.
    • 작은 배치의 decode처럼 메모리 바운드인 일에서 효과가 가장 큽니다.

    2. SRAM에 가중치를 담는 추론 칩

    • Groq의 는 칩 안 SRAM 수백 MB에 가중치를 담아, HBM을 오가는 지연을 없앴습니다. 대신 칩 하나의 용량이 작아 큰 모델에는 칩이 아주 많이 필요합니다.
    • 2025년 12월 NVIDIA는 Groq의 추론 기술을 비독점으로 라이선스하고 핵심 인력을 데려왔습니다. CNBC는 거래 규모를 약 200억 달러로 보도했습니다.
    꼭 알아 둘 것에이전트와 실시간 음성처럼 바로 답해야 하는 추론이 늘면서, 처리량만큼 지연이 중요해지고 있습니다.
    PART 3

    Coalesced Access (병합 접근)

    여기까지가 대역폭과 지연이라는 두 숫자였습니다. 이제 GPU 안에서 그 대역폭을 제대로 쓰는 방법, 병합 접근으로 넘어가겠습니다.

    3.1

    정의

    , 영어로 Coalesced Access는 warp의 32개 스레드가 이어진 주소를 읽어, 하드웨어가 이를 적은 수의 메모리 요청으로 합쳐 처리하는 접근 방식입니다.

    • 3회차에서 본 , 즉 함께 움직이는 32개 스레드 묶음이 기준입니다.
    • 32개 스레드가 4바이트씩 이어서 읽으면 128바이트이고, 32바이트 섹터 4개로 한 번에 처리됩니다.
    • 따로 켜는 기능이 아닙니다. 주소 패턴이 맞으면 하드웨어가 알아서 합칩니다.
    3.2

    등장 배경

    • DRAM은 한 번 열면 이어진 구간을 통째로 읽는 구조라서, 작게 흩어진 접근에 아주 비효율적입니다.
    • 그런데 GPU는 warp의 32개 스레드가 같은 명령을 동시에 실행합니다. 주소만 잘 맞으면 요청을 묶을 수 있습니다.
    "그럼 warp의 요청 32개를 한 덩어리로 합쳐서, 한 번에 가져오자!"그래서 등장한 것이 바로 병합 접근입니다.
    • 2007년 CUDA 1.0부터 가장 중요한 최적화 규칙이었습니다. 처음에는 반 warp, 즉 16개 스레드가 정렬된 순서로 읽어야만 합쳐졌습니다.
    • 2010년 Fermi부터는 캐시 줄 단위로 합쳐지면서 규칙이 크게 느슨해졌습니다.
    3.3

    구조

    단위크기하는 일
    32바이트메모리에서 가져오는 가장 작은 단위
    캐시 줄128바이트, 섹터 4개L1과 L2가 관리하는 단위
    warp 요청스레드 32개의 주소한 명령의 주소를 모아 몇 개 섹터가 필요한지 정함
    • 효율은 필요한 바이트를 실제로 가져온 바이트로 나눈 값입니다.
    • 32개 스레드가 float를 이어서 읽으면 128바이트가 필요하고, 128바이트를 가져오니 효율은 100%입니다.
    3.4

    작동 방식

    1. 주소 모으기: warp가 메모리 읽기 명령 하나를 실행하면, 32개 스레드의 주소가 한꺼번에 나옵니다.
    2. 섹터 세기: 하드웨어가 그 주소들이 몇 개의 32바이트 섹터에 걸쳐 있는지 셉니다.
    3. 섹터만큼 가져오기: 필요한 섹터만 L2나 HBM에서 가져옵니다.
    4. 나눠 주기: 가져온 데이터를 각 스레드에 나눠 줍니다.
    // 병합: 스레드 i가 i번째 원소 → 이어진 128B
float v = a[blockIdx.x * blockDim.x + threadIdx.x];

// 비병합(stride): 스레드 i가 i*32번째 원소 → 섹터 32개를 따로 읽음 (효율 1/8)
float w = a[(blockIdx.x * blockDim.x + threadIdx.x) * 32];
    • : {x, y, z} 구조체를 배열로 늘어놓으면, x만 읽어도 y와 z까지 함께 끌려옵니다. x끼리, y끼리 따로 배열로 두면 병합됩니다.
    • 행렬 전치: 패턴상 병합이 안 되면 Shared Memory로 한 번 받은 뒤 순서를 바꿔 씁니다.
    Q. PyTorch만 쓰는데 이걸 신경 써야 하나요?

    대부분은 라이브러리가 처리합니다. 다만 transpose나 permute 뒤에 .contiguous() 없이 연산하면, 메모리상 순서가 흩어진 텐서를 읽게 되어 느려질 수 있습니다. 텐서의 stride, 즉 메모리 배치를 알면 원인을 찾기 쉽습니다.

    3.5

    이점

    • 대역폭을 끝까지 씁니다: 같은 대역폭으로 실제로 쓸 데이터를 가장 많이 가져옵니다.
    • 차이가 큽니다: 병합하지 않은 코드와 비교하면 몇 배에서 몇십 배까지 차이가 납니다.
    • 캐시와 의 부담도 줄어듭니다: 요청 수가 줄어서, 다른 warp의 요청이 덜 밀립니다.
    3.6

    부재 시 문제

    병합이 되지 않는다고 가정해 보면, 이런 문제가 생깁니다.

    • 4바이트가 필요한데 32바이트씩 가져와서, 효율이 8분의 1이 됩니다.
    • 예를 들어 의 3.35TB/s도, 효율이 8분의 1이면 실제로 쓰는 데이터는 약 420GB/s 수준입니다. 예시 계산입니다.
    3.7

    단점

    • 데이터 배치를 GPU에 맞춰야 합니다: CPU에서 편한 구조체 배열이 GPU에서는 느릴 수 있어, 두 쪽이 충돌합니다.
    • 불규칙한 접근은 본래 어렵습니다: 희소 행렬, 그래프, 임베딩 조회처럼 주소가 데이터에 따라 정해지는 일은 병합하기 어렵습니다.
    • 눈에 잘 띄지 않습니다: 코드는 맞게 돌아가고 느리기만 해서, 로 봐야 알 수 있습니다.
    3.8

    단점 극복을 위한 대안 기술

    1. 데이터 배치 바꾸기

    • 뜻: 구조체 배열을 배열 구조체로 바꾸고, 시작 주소를 128바이트에 맞춰 정렬하거나 빈칸을 채웁니다.
    • 해결하는 단점: 데이터 배치가 GPU에 맞지 않는 문제를 풉니다.

    2. 를 거쳐 재배치

    • 뜻: 병합되는 순서로 읽어 Shared Memory에 담고, 거기서 원하는 순서로 꺼내 씁니다.
    • 해결하는 단점: 전치처럼 패턴상 병합이 안 되는 문제를 풉니다.

    3. 벡터 단위로 읽기

    • 뜻: float4처럼 스레드 하나가 16바이트씩 한 번에 읽습니다.
    • 해결하는 단점: 요청 수 자체를 줄입니다.

    4. (Hopper부터)

    • 뜻: 여러 차원의 타일을 하드웨어가 통째로 복사합니다. 주소 계산과 병합을 하드웨어가 맡습니다. 3회차와 5회차에서 봤습니다.
    • 해결하는 단점: 주소 패턴을 손으로 맞추는 부담을 줄입니다.

    5. 캐시 활용

    • 뜻: 병합이 안 되는 불규칙 접근은 L1과 L2 적중률로 보완합니다.
    • 해결하는 단점: 본래 병합이 어려운 접근의 손해를 줄입니다.
    3.9

    대안과의 비교

    꼭 알아 둘 것같은 warp의 스레드는 이어진 주소를 읽게 합니다. 대역폭을 늘리는 가장 싼 방법은 이미 있는 대역폭을 낭비하지 않는 것입니다.
    3.10

    최신 트렌드

    1. 병합을 하드웨어가 맡습니다

    • Hopper의 TMA는 타일 단위로 주소를 계산하고 복사해서, 스레드마다 주소를 맞추는 일을 하드웨어로 넘겼습니다. Blackwell도 이 방식을 이어 갑니다.

    2. 병합을 컴파일러가 맡습니다

    • NVIDIA는 2025년 12월 CUDA 13.1과 함께 Python용 타일 프로그래밍 도구 을 내놓았고, 2026년 CUDA 13.3에 C++ 버전을 넣었습니다. 5회차 2.10에서 본 내용입니다.
    • 타일 단위로 계산만 적으면, 메모리를 어떤 순서로 읽을지는 컴파일러가 정합니다. 도 같은 방향입니다.
    꼭 알아 둘 것주소를 맞추는 일은 점점 하드웨어와 컴파일러 몫이 됩니다. 그래도 데이터를 어떤 배치로 저장할지는 여전히 사람이 정합니다.
    PART 4

    Pinned Memory · Unified Memory

    여기까지가 GPU 안의 이야기였습니다. 마지막으로 CPU와 GPU 사이에서 데이터를 빠르고 쉽게 옮기는 방법, Pinned Memory와 Unified Memory를 보겠습니다.

    4.1

    정의

    는 OS가 옮기지 못하게 고정해 둔 CPU 쪽 메모리이고, 는 CPU와 GPU가 같은 주소로 쓰고, 필요한 데이터가 자동으로 옮겨 가는 메모리입니다.

    • Pageable Memory: 일반 malloc으로 잡은 메모리입니다. OS가 언제든 다른 자리로 옮기거나 디스크로 내릴 수 있습니다.
    • Pinned Memory: page-locked memory라고도 부릅니다. cudaMallocHost나 cudaHostAlloc으로 잡습니다.
    • Unified Memory: cudaMallocManaged로 잡고, CPU와 GPU가 같은 포인터를 씁니다. 접근하는 쪽으로 페이지 단위로 옮겨 갑니다.
    • CPU 쪽 메모리, 즉 Host Memory 자체는 7회차에서 다룹니다.
    4.2

    등장 배경

    • GPU의 복사 엔진, 즉 는 물리 주소가 고정된 메모리만 직접 읽을 수 있습니다.
    • 그래서 일반 메모리를 보내면, 드라이버가 먼저 임시 고정 버퍼로 한 번 더 복사한 뒤 보냈습니다.
    • 또 cudaMemcpy로 모든 이동을 손으로 관리하는 일은 번거롭고 실수가 잦았습니다.
    "그럼 보낼 메모리는 처음부터 고정해 두고, 주소도 CPU와 GPU가 하나로 쓰자!"그래서 등장한 것이 바로 Pinned Memory와 Unified Memory입니다.
    • Pinned Memory는 CUDA 초기부터 있었습니다.
    • Unified Memory는 2014년 CUDA 6에서 나왔고, 2016년 Pascal부터 페이지 폴트로 자동으로 옮기고 VRAM보다 큰 데이터도 다룰 수 있게 됐습니다.
    4.3

    구조

    1. 메모리 종류

    종류할당GPU로 가는 방식특징
    Pageablemalloc드라이버가 임시 고정 버퍼로 복사한 뒤 전송느리고, 전송이 끝날 때까지 기다림
    PinnedcudaMallocHost복사 엔진이 직접 읽어 감빠르고, 계산과 동시에 전송 가능
    UnifiedcudaMallocManaged접근할 때 페이지가 옮겨 감편하지만, 속도를 예측하기 어려움
    cudaHostAlloc 매핑GPU가 PCIe로 CPU 메모리를 바로 읽음한 번 읽을 때는 좋고, 반복하면 매우 느림

    2. 하드웨어로 묶인 메모리

    • Grace Hopper와 Grace Blackwell, 즉 GH200과 GB200은 로 CPU와 GPU를 900GB/s로 잇습니다.
    • 두 쪽 메모리가 하드웨어로 일관되게 묶여 있어서, 옮기지 않고도 서로의 메모리를 바로 읽습니다.

    3.

    • Linux의 HMM, Heterogeneous Memory Management를 쓰면 일반 malloc 메모리도 GPU에서 접근할 수 있습니다.
    • 오픈 커널 모듈 드라이버와 CUDA 12.2 이상이 필요합니다.
    4.4

    작동 방식

    1. Pinned Memory로 보내기

    1. 고정하기: CPU 메모리 일부를 고정합니다. OS는 이 자리를 옮기지 않습니다.
    2. 바로 보내기: cudaMemcpyAsync로 요청하면, GPU의 복사 엔진이 PCIe로 바로 읽어 갑니다.
    3. 겹치기: 복사하는 동안 GPU는 이전 배치를 계산합니다.
    # PyTorch: Pinned Memory와 비동기 전송
loader = DataLoader(ds, batch_size=64, num_workers=8, pin_memory=True)
for x, y in loader:
    x = x.to("cuda", non_blocking=True)   # pinned라서 계산과 겹쳐 복사

    2. Unified Memory로 쓰기

    1. 할당하기: cudaMallocManaged로 잡은 포인터 하나를 CPU와 GPU가 함께 씁니다.
    2. 없으면 멈추기: GPU가 아직 자기 쪽에 없는 페이지를 읽으면 가 납니다.
    3. 옮기기: 드라이버가 그 페이지를 GPU로 옮긴 뒤 이어서 실행합니다.
    4. 미리 옮기기: cudaMemPrefetchAsync로 미리 옮겨 두면 페이지 폴트를 피합니다.
    float* data; cudaMallocManaged(&data, bytes);   // CPU·GPU 공용 포인터
cudaMemPrefetchAsync(data, bytes, device_id);   // 미리 GPU로 옮겨 페이지 폴트 방지
kernel<<<g, b>>>(data);
    4.5

    이점

    • Pinned, 빠릅니다: 중간 복사가 없어서 전송 속도가 PCIe 한계에 가까워집니다.
    • Pinned, 겹칠 수 있습니다: 계산과 전송을 동시에 해서 데이터 로딩이 GPU를 붙잡지 않습니다. 와 RDMA도 고정된 메모리를 전제로 합니다.
    • Unified, 코드가 단순합니다: 이동을 손으로 관리하지 않아도 됩니다. 포인터로 이어진 복잡한 자료구조도 그대로 나눠 씁니다.
    • Unified, VRAM보다 큰 데이터를 다룹니다: 이걸 oversubscription, 용량 초과라고 합니다.
    Q. pin_memory=True가 빠른 이유는 무엇인가요?

    두 가지입니다. 첫째, 임시 고정 버퍼로 한 번 더 복사하는 단계가 없습니다. 둘째, non_blocking=True로 비동기 전송을 해서 계산과 전송을 겹칠 수 있습니다.

    4.6

    부재 시 문제

    가 없다고 가정해 보면, 전송할 때마다 중간 복사가 생기고 비동기 전송도 못 합니다. 그러면 GPU가 데이터 로딩을 기다리며 놉니다.

    Unified Memory가 없다고 가정해 보면, 모든 이동을 손으로 관리해야 합니다. VRAM보다 큰 데이터는 직접 쪼개서 여러 번 보내야 합니다.

    4.7

    단점

    • Pinned를 너무 많이 잡으면 느려집니다: OS가 쓸 수 있는 메모리가 줄어 시스템 전체가 느려지고, 할당 자체도 오래 걸립니다.
    • 컨테이너에서 막힐 수 있습니다: 고정할 수 있는 메모리 한도, 즉 ulimit -l의 memlock과 Pod의 메모리 limit에 걸립니다. limit은 16회차에서 다룹니다.
    • 는 속도를 예측하기 어렵습니다: 페이지 폴트가 잦으면 직접 복사하는 것보다 훨씬 느립니다.
    Q. 그럼 모든 메모리를 Pinned로 잡으면 되지 않나요?

    안 됩니다. Pinned 메모리는 OS가 옮기거나 디스크로 내릴 수 없어서, 많이 잡으면 시스템 메모리가 모자라고 컨테이너에서는 메모리 한도에 걸립니다. 전송용 버퍼에만 필요한 만큼 씁니다.

    Q. Unified Memory를 쓰면 VRAM보다 큰 모델도 돌릴 수 있나요?

    기술적으로는 됩니다. 하지만 넘친 부분이 PCIe로 계속 오가서 매우 느려집니다. 학습과 추론에서는 오프로딩, 양자화, 여러 GPU에 나눠 담기가 더 현실적입니다.

    4.8

    단점 극복을 위한 대안 기술

    1. 미리 옮기기와 힌트 주기

    • 뜻: cudaMemPrefetchAsync로 미리 옮기고, cudaMemAdvise로 이 데이터를 주로 어디서 읽는지 알려 줍니다.
    • 해결하는 단점: Unified Memory의 페이지 폴트를 줄입니다.

    2. Pinned 버퍼 재사용

    • 뜻: 큰 Pinned 버퍼를 한 번만 잡아 두고 계속 다시 씁니다. PyTorch 같은 프레임워크가 안에서 쓰는 방식입니다.
    • 해결하는 단점: Pinned를 자주, 많이 잡는 문제를 피합니다.

    3. 하드웨어로 묶인 메모리

    • 뜻: GH200과 GB200의 NVLink-C2C처럼 CPU와 GPU 메모리를 하드웨어로 묶습니다.
    • 해결하는 단점: PCIe를 거치는 이동과 페이지 폴트 비용 자체를 줄입니다.

    4.

    • 뜻: 디스크에서 GPU로 CPU 메모리를 거치지 않고 바로 보냅니다. 9회차에서 다룹니다.
    • 해결하는 단점: Host Memory를 거치는 단계 자체를 없앱니다.
    4.9

    대안과의 비교

    방식전송 속도코드 난이도주의할 점
    Pageable과 cudaMemcpy낮음 (중간 복사)쉬움전송이 끝날 때까지 기다림
    Pinned와 cudaMemcpyAsync높음 (PCIe 한계에 가까움)중간너무 많이 잡지 않기
    Unified Memory접근 패턴에 따라 크게 다름가장 쉬움페이지 폴트, 미리 옮기기 필요
    GPU가 PCIe로 직접 읽음중간반복해서 읽으면 매우 느림
    하드웨어로 묶인 메모리 (Grace 계열)매우 높음쉬움특정 하드웨어가 필요
    꼭 알아 둘 것CPU에서 GPU로 자주 보내는 데이터는 Pinned Memory에 두고, 계산과 겹쳐서 보냅니다. PyTorch에서는 pin_memory=True와 non_blocking=True 두 줄이 바로 이것입니다.
    4.10

    최신 트렌드

    1. CPU 메모리를 GPU 메모리처럼 씁니다

    • 2026년 NVIDIA는 Vera CPU를 발표했습니다. GPU와 로 1.8TB/s로 묶여, GH200의 900GB/s보다 두 배입니다.
    • NVIDIA는 이 속도가 PCIe Gen6의 약 7배라고 밝혔습니다. CPU 메모리를 옮기지 않고 GPU 메모리처럼 쓰는 방향입니다.

    2. KV 캐시를 여러 층에 나눠 둡니다

    • 추론 엔진은 를 VRAM에서 CPU 쪽 Pinned Memory로, 다시 SSD로 내려 두는 기능을 갖춰 가고 있습니다.
    • NVIDIA는 2026년 1월 CES에서 BlueField-4 기반 Inference Context Memory Storage를 발표했습니다. GPU와 기존 스토리지 사이에 KV 캐시 전용 층을 두는 구성이고, 2026년 3월 GTC에서 BlueField-4 STX라는 참조 설계로 넓혔습니다.
    꼭 알아 둘 것CPU와 GPU 사이의 벽이 낮아지고 있습니다. 그래도 어떤 데이터를 어디에 둘지 정하는 일은 여전히 성능을 크게 좌우합니다.

    여기까지가 메모리의 속도였습니다. CPU와 GPU를 잇는 길, PCIe와 Host Memory는 7회차에서 다룹니다.
