    PART 1

    VRAM과 HBM (Video RAM · High Bandwidth Memory)

    가장 바깥, 가장 큰 칸부터 보겠습니다. 모델과 데이터가 처음 올라가는 곳입니다.

    1.1

    정의

    은 GPU가 혼자 쓰는 메인 메모리이고, HBM은 데이터센터 GPU가 VRAM을 만드는 방식입니다.

    • 모델 가중치, 계산 중간값, KV 캐시처럼 GPU가 계산할 모든 데이터가 VRAM에 올라가야 합니다.
    • VRAM은 역할의 이름이고, HBM과 GDDR은 그 VRAM을 만드는 기술의 이름입니다. 게이밍 GPU는 GDDR, 데이터센터 GPU는 HBM을 씁니다.
    • H100 SXM은 HBM3 80GB를 쓰고, 1초에 3.35테라바이트를 읽고 씁니다.
    Q. 기초 · 왜 이름에 Video가 붙어 있나요?

    처음에는 화면에 내보낼 그림 한 장, 즉 프레임 버퍼와 텍스처를 담으려고 만든 메모리였기 때문입니다. 지금은 AI 모델을 담는 그릇이 됐지만 이름은 그대로 남았습니다.

    1.2

    등장 배경

    • GPU의 계산 속도는 세대마다 크게 늘었는데, 메모리가 데이터를 대 주는 속도는 그만큼 늘지 못했습니다. 이걸 이라고 부릅니다.
    • GDDR은 선 하나당 속도를 계속 올려 버텼지만, 전력과 신호 품질에서 한계가 왔습니다.
    "그럼 메모리 칩을 위로 쌓아서, GPU 바로 옆에 아주 넓은 길로 붙이자!"그래서 등장한 것이 바로 HBM입니다.
    • 2013년 JEDEC 표준이 됐고, 2015년 AMD Radeon R9 Fury에 처음 들어갔습니다.
    • NVIDIA는 2016년 P100부터 데이터센터 GPU에 HBM을 씁니다.
    1.3

    구조

    1. HBM 스택 하나

    • DRAM 칩 여러 장을 위로 쌓고, 칩을 뚫는 전극으로 위아래를 잇습니다. 이 전극을 , 실리콘 관통 전극이라고 합니다.
    • 맨 아래에는 신호를 정리하는 베이스 다이가 있고, 그 위에 DRAM 다이를 8장에서 16장 쌓습니다.
    • 스택 하나가 GPU와 주고받는 길은 1,024개입니다. HBM4는 2,048개로 두 배가 됐습니다. GDDR 칩 하나는 32개입니다.

    2. 패키지 안의 배치

    • GPU 다이와 HBM 스택을 실리콘 인터포저라는 얇은 판 위에 나란히 올립니다. TSMC의 CoWoS가 대표적인 방식입니다.
    • H100 SXM은 GPU 다이 옆에 HBM3 스택 5개를 켜서 씁니다.

    3. VRAM에 올라가는 것

    올라가는 것하는 일언제
    모델 가중치모델 그 자체학습과 추론 모두
    그래디언트 · 옵티마이저 상태가중치를 얼마나 고칠지 계산한 값학습
    활성값 (activation)층마다 나온 중간 결과학습 (역전파에 다시 씀)
    KV 캐시앞서 읽은 토큰의 계산 결과추론, 20회차에서 다룹니다
    CUDA 컨텍스트프로그램을 GPU에서 돌리기 위한 기본 공간항상, 프로세스마다 수백 MB
    1.4

    작동 방식

    1. 자리 잡기: 프로그램이 cudaMalloc으로 VRAM에 자리를 잡습니다. PyTorch는 큰 덩어리를 미리 잡아 두고 안에서 나눠 씁니다.
    2. 옮겨 오기: CPU 쪽 메모리에 있던 데이터를 PCIe로 VRAM에 복사합니다. 7회차에서 다룹니다.
    3. 동시에 읽기: GPU의 메모리 컨트롤러가 스택마다 연결된 여러 채널로 한꺼번에 읽고 씁니다. 길 하나는 느려도 길이 아주 많아서 전체 속도가 큽니다.
    4. 모자라면 멈추기: 자리가 모자라면 CPU처럼 디스크로 넘기지 않고, 바로 out of memory 오류, 줄여서 으로 멈춥니다.
    계산해 보기H100 SXM의 대역폭은 길 5,120개, 즉 스택 5개 곱하기 1,024개에, 길 하나의 속도를 곱한 값입니다. 길 하나가 1초에 약 5.2기가비트를 보내면, 모두 약 3.35테라바이트입니다.
    Q. nvidia-smi에서 메모리가 꽉 차 보이는데, 정말 다 쓰고 있나요?

    꼭 그렇지 않습니다. PyTorch나 vLLM은 메모리를 미리 크게 잡아 두고 안에서 재사용합니다. vLLM은 기본으로 VRAM의 90%를 먼저 잡습니다. nvidia-smi는 잡아 둔 양을 보여 줘서, 실제 쓰는 양은 프레임워크의 메모리 통계로 봐야 합니다.

    1.5

    이점

    • 대역폭이 큽니다: H100 SXM은 3.35TB/s입니다. 을 쓰는 RTX 5090은 약 1.8TB/s입니다.
    • 전력을 덜 씁니다: GPU 바로 옆이라 거리가 짧고, 길 하나의 속도가 낮아 비트당 전력이 적습니다.
    • 보드가 단순해집니다: 큰 용량이 패키지 안에 들어가서, 보드에 메모리 칩을 둘러 깔 필요가 없습니다.
    • 큰 모델을 한 장에 담습니다: 용량이 클수록 GPU를 나눠 쓰는 통신 비용이 줄어듭니다.
    Q. 메모리가 성능을 좌우한다는 대표 사례가 있나요?

    H100과 H200은 계산 칩이 같습니다. H200은 메모리만 HBM3E 141GB, 4.8TB/s로 바꿨는데, LLM 추론이 크게 빨라졌습니다. 토큰을 하나씩 만드는 단계는 계산보다 가중치를 읽어 오는 속도에 묶여 있기 때문입니다.

    1.6

    부재 시 문제

    없이 GDDR만 있다고 가정해 보면, 이런 문제가 생깁니다.

    • 같은 계산 성능이라도 데이터를 대 주지 못해서, LLM의 토큰 생성 속도가 크게 떨어집니다.
    • GPU 한 장의 용량이 작아서 큰 모델을 여러 장에 나눠 담아야 하고, 그만큼 통신이 늘어납니다.

    VRAM 자체가 모자라면, 모델이 올라가지 않아 학습과 추론이 시작조차 되지 않습니다.

    1.7

    단점

    • 비싸고 귀합니다: 쌓고 뚫고 붙이는 공정이 어렵고, HBM과 생산량이 GPU 출하량을 정합니다.
    • 용량을 늘리기 어렵습니다: GPU 옆에 놓을 수 있는 스택 수가 정해져 있습니다. 더 높이 쌓으면 수율과 발열 문제가 커집니다.
    • 나중에 늘릴 수 없습니다: GPU와 한 몸이라 증설이 안 됩니다.
    • GPU 개수 단위로만 나눠집니다: Kubernetes 기본 설정은 GPU 개수만 셉니다. VRAM 양으로 나눠 주는 방법은 14회차에서 봅니다.
    1.8

    단점 극복을 위한 대안 기술

    1. 양자화

    • 뜻: 숫자를 더 적은 비트로 저장해 모델 크기를 줄입니다. FP16을 FP8이나 4비트로 바꾸면 절반에서 4분의 1이 됩니다. 4회차에서 봤습니다.
    • 해결하는 단점: 용량이 모자라 모델이 올라가지 않는 문제를 줄입니다.

    2. 나눠 담기

    • 뜻: 모델을 여러 GPU에 쪼개 담습니다. Tensor Parallelism과 FSDP가 대표적이고, 17회차와 18회차에서 다룹니다.
    • 해결하는 단점: GPU 한 장의 용량 한계를 넘습니다. 대신 통신이 늘어납니다.

    3. 오프로딩

    • 뜻: 당장 안 쓰는 데이터를 CPU 메모리나 SSD로 내려놓습니다. 옵티마이저 상태나 KV 캐시를 주로 내립니다.
    • 해결하는 단점: VRAM을 나중에 늘릴 수 없는 문제를 우회합니다. 대신 PCIe를 거치는 만큼 느려집니다.

    4. GDDR · LPDDR 같은 다른 메모리

    • 뜻: 대역폭이 덜 필요한 곳에는 값싼 GDDR7을 쓰고, CPU 쪽 LPDDR5X를 GPU가 함께 쓰게 붙입니다. Grace CPU와 NVLink-C2C가 그 예입니다.
    • 해결하는 단점: HBM이 비싸고 귀한 문제를 피합니다.

    PART 2

    Global Memory와 Shared Memory

    여기까지가 하드웨어로 본 VRAM이었습니다. 이제 프로그램이 보는 메모리, Global Memory와 Shared Memory로 넘어가겠습니다.

    2.1

    정의

    는 모든 스레드가 함께 쓰는 크고 느린 공간이고, Shared Memory는 같은 블록의 스레드끼리 쓰는 SM 안의 작고 빠른 공간입니다.

    • Global Memory는 1부에서 본 VRAM을 프로그램 쪽에서 부르는 이름입니다. 커널이 끝나도 남아 있습니다.
    • Shared Memory는 SM 안의 SRAM입니다. 블록이 끝나면 사라지고, 코드에서 __shared__로 선언합니다.
    • 3회차에서 본 블록이 바로 Shared Memory를 함께 쓰는 단위입니다.
    Q. 기초 · SRAM과 DRAM은 무엇이 다른가요?

    DRAM은 축전기에 전기를 담아 0과 1을 기억해서 작고 싸지만, 주기적으로 다시 채워야 하고 느립니다. SRAM은 트랜지스터 여섯 개로 한 비트를 붙잡아 빠르지만, 자리를 많이 차지해 비쌉니다. 그래서 큰 VRAM은 DRAM, SM 안의 작은 메모리는 SRAM입니다.

    2.2

    등장 배경

    • Global Memory에서 숫자 하나를 가져오는 데 수백 사이클이 걸립니다.
    • 행렬 곱셈은 같은 숫자를 여러 번 다시 읽는데, 그때마다 VRAM까지 다녀오면 계산 유닛이 놉니다.
    • CPU처럼 하드웨어 캐시에 맡기면, 수만 개 스레드가 캐시를 서로 밀어내 재사용이 잘 안 됐습니다.
    "그럼 무엇을 가까이 둘지 프로그래머가 직접 정하는 빠른 공간을 SM 안에 두자!"그래서 2006년 G80에서 등장한 것이 바로 입니다.
    • G80은 SM 하나에 16KB였고, H100은 최대 228KB입니다.
    2.3

    구조

    1. 두 공간의 위치

    • Shared Memory는 SM마다 따로 있고, 그 안에서도 블록마다 칸을 나눠 받습니다. 다른 블록의 칸은 볼 수 없습니다.
    • Global Memory는 하나라서, 모든 블록이 같은 주소를 봅니다.

    2. Shared Memory 안쪽

    구성하는 일H100 SM 1개당
    SRAM 한 덩어리L1 캐시와 Shared Memory가 나눠 씁니다256KB
    Shared Memory 몫블록에 나눠 줍니다최대 228KB, 블록 하나는 최대 227KB
    동시에 읽을 수 있게 32칸으로 나눈 구역32개, 4바이트 단위

    3. Global 영역에 있는 다른 공간

    • Local Memory: 레지스터가 모자랄 때 넘친 값이 가는 곳입니다. 이름은 Local이지만 실제로는 VRAM에 있습니다. 3.7에서 봅니다.
    • Constant Memory: 모든 스레드가 읽기만 하는 작은 상수 공간입니다.
    2.4

    작동 방식

    행렬 곱셈에서 쓰는 방법, 즉 을 따라가 보겠습니다.

    1. 한 번 가져오기: 블록의 스레드들이 Global Memory에서 행렬 조각, 즉 타일을 나눠 읽어 Shared Memory에 채웁니다.
    2. 기다리기: __syncthreads()로 모든 스레드가 다 채울 때까지 기다립니다.
    3. 여러 번 쓰기: 스레드들이 Shared Memory의 타일을 여러 번 읽어 계산합니다. 이때는 VRAM에 가지 않습니다.
    4. 결과만 쓰기: 다 계산한 결과만 Global Memory에 씁니다.
    __global__ void tile_example(const float* g_in, float* g_out) {
    __shared__ float tile[32][32];                 // 블록이 함께 쓰는 공간
    tile[threadIdx.y][threadIdx.x] = g_in[/*...*/]; // Global에서 한 번만 읽기
    __syncthreads();                               // 모두 채울 때까지 대기
    // tile을 여러 번 읽어 계산 (Global에 다시 가지 않음)
}
    Q. 뱅크 충돌은 무엇인가요?

    Shared Memory는 32개 뱅크로 나뉘어 있어서, warp의 32개 스레드가 서로 다른 뱅크를 읽으면 한 번에 끝납니다. 여러 스레드가 같은 뱅크의 다른 주소를 읽으면 차례로 처리해서 느려집니다. 배열 폭을 32에서 33으로 한 칸 늘려 피하는 방법이 흔합니다.

    2.5

    이점

    • VRAM 왕복을 줄입니다: 32 곱하기 32 타일이면, 숫자 하나를 VRAM에서 한 번 읽어 32번 씁니다.
    • 훨씬 빠릅니다: Shared Memory는 수십 사이클, Global Memory는 수백 사이클이라 대략 10배 차이입니다.
    • 블록 안에서 값을 나눕니다: 스레드끼리 중간 결과를 주고받는 통로가 됩니다.
    • 결과가 예측됩니다: 캐시처럼 운에 맡기지 않고, 무엇이 남을지 프로그래머가 압니다.
    2.6

    부재 시 문제

    Shared Memory가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 같은 숫자를 다시 읽을 때마다 VRAM이나 캐시에 기대야 해서, Tensor Core가 데이터를 기다리며 놉니다.
    • 블록 안 스레드끼리 값을 주고받으려면 VRAM을 거쳐야 합니다.
    • FlashAttention처럼 중간 결과를 칩 안에서 끝내는 기법을 쓸 수 없습니다.
    2.7

    단점

    • 작습니다: SM 하나에 수백 KB뿐입니다. 블록이 많이 쓰면 SM에 올라갈 블록 수가 줄어 이 떨어집니다. 2회차 4.4에서 계산해 봤습니다.
    • 신경 쓸 게 많습니다: 뱅크 충돌, 동기화, 타일 크기를 프로그래머가 직접 맞춰야 합니다.
    • 블록이 끝나면 사라집니다: 커널이나 블록을 넘어 남기려면 Global Memory에 써야 합니다.
    • 다른 SM과 나누지 못합니다: 원래는 같은 SM의 같은 블록만 볼 수 있습니다. 2.8에서 봅니다.
    2.8

    단점 극복을 위한 대안 기술

    1. 비동기 복사와

    • 뜻: Global Memory에서 Shared Memory로 옮기는 일을 계산과 동시에 진행합니다. Ampere의 cp.async, Hopper의 TMA가 있습니다. 3회차 PART 5에서 봤습니다.
    • 해결하는 단점: 옮기는 동안 계산 유닛이 쉬는 문제를 줄입니다.

    2. Distributed Shared Memory (H100부터)

    • 뜻: 2회차에서 본 Thread Block Cluster 안에서, 다른 SM의 Shared Memory를 직접 읽고 씁니다.
    • 해결하는 단점: Shared Memory를 다른 SM과 나누지 못하는 문제를 풉니다.

    3. 타일 단위 프로그래밍 도구

    • 뜻: Triton이나 cuTile처럼 타일 단위로 코드를 쓰면, Shared Memory 배치와 동기화를 컴파일러가 맡습니다.
    • 해결하는 단점: 뱅크 충돌과 동기화를 손으로 맞추는 부담을 줄입니다.

    PART 3

    Register (레지스터)

    여기까지가 블록이 함께 쓰는 공간이었습니다. 이제 스레드 하나가 혼자 쓰는 가장 빠른 공간, 레지스터로 넘어가겠습니다.

    3.1

    정의

    는 스레드마다 따로 주어지는, GPU에서 가장 빠르고 가장 작은 저장 공간입니다.

    • 계산의 재료와 결과가 직접 오가는 곳입니다. 코드의 지역 변수가 주로 여기에 있습니다.
    • 한 칸은 32비트이고, 스레드 하나는 최대 255칸까지 씁니다. 몇 칸을 쓸지는 컴파일러가 정합니다.
    • 3회차에서 본 스레드가 바로 레지스터를 가진 단위입니다.
    3.2

    등장 배경

    • 계산 유닛은 메모리에서 바로 계산하지 못하고, 레지스터에 있는 값으로만 계산합니다. 이건 CPU도 같습니다.
    • 그런데 GPU는 수천 개 를 번갈아 실행합니다. CPU처럼 바꿀 때마다 레지스터를 메모리에 저장하고 다시 불러오면 너무 느립니다.
    "그럼 올라온 모든 스레드의 레지스터를 처음부터 칩 안에 다 두자!"그래서 2006년 G80부터 GPU가 갖게 된 것이 바로 큰 레지스터 파일입니다.
    • G80은 SM 하나에 레지스터 8,192칸, 32KB였습니다. H100은 65,536칸, 256KB입니다.
    3.3

    구조

    • 하나에 레지스터 65,536칸, 칸마다 32비트라서 256KB입니다.
    • H100 SXM은 SM이 132개라서, 레지스터를 모두 합치면 약 33MB입니다. L2 캐시 50MB와 맞먹는 크기입니다.
    • SM의 네 구역이 64KB씩 나눠 갖고, 각 구역의 warp들이 다시 나눠 씁니다.
    항목값 (H100)
    한 칸의 크기32비트
    SM 하나의 칸 수65,536칸, 256KB
    스레드 하나의 최대 칸 수255칸
    GPU 전체약 33MB
    3.4

    작동 방식

    1. 칸 수 정하기: 컴파일할 때 스레드 하나가 쓸 칸 수가 정해집니다. nvcc --resource-usage로 확인합니다.
    2. 나눠 주기: 블록이 SM에 올라가면, 스레드 수 곱하기 칸 수만큼 레지스터를 떼어 줍니다. 블록이 끝날 때까지 그대로입니다.
    3. 바로 바꾸기: warp를 바꿀 때 레지스터를 옮기지 않습니다. 이미 다 칩 안에 있어서 바꾸는 비용이 거의 없습니다.
    4. 넘치면 내려놓기: 칸이 모자라면 컴파일러가 일부 값을 Local Memory로 내립니다. 이걸 , 영어로 spill이라고 합니다.
    꼭 알아 둘 것스레드 하나가 레지스터를 두 배로 쓰면, SM에 올라갈 스레드는 절반이 됩니다. 2회차 4.4의 점유율 계산이 바로 이 이야기입니다.
    3.5

    이점

    • 가장 빠릅니다: 약 1 사이클 안에 읽고 씁니다.
    • warp를 바꾸는 비용이 거의 없습니다: 모든 warp의 레지스터가 칩 안에 있어서, 기다리는 warp 대신 다른 warp를 바로 실행합니다. 2회차의 이 여기서 나옵니다.
    • 재사용에 강합니다: 행렬 곱셈의 부분합처럼 계속 쓰는 값을 레지스터에 두면, 메모리에 다시 가지 않습니다.
    3.6

    부재 시 문제

    레지스터 파일이 작다고 가정해 보면, 이런 문제가 생깁니다.

    • 중간값을 매번 메모리에 썼다 읽어야 해서, 계산 속도가 메모리 속도로 떨어집니다.
    • warp를 바꿀 때마다 레지스터를 저장하고 복원해야 해서, 수천 개 warp를 번갈아 돌리는 방식이 무너집니다.
    3.7

    단점

    • 나눠 쓰는 자원입니다: 스레드 하나가 많이 쓰면 SM에 올라갈 스레드가 줄어 이 떨어집니다.
    • 줄이면 넘칩니다: 억지로 칸 수를 줄이면 넘친 값이 VRAM의 Local Memory로 가서 오히려 느려집니다.
    • 직접 다루기 어렵습니다: 몇 칸을 쓸지는 컴파일러가 정해서, 프로그래머는 간접적으로만 조절합니다.
    • Tensor Core 결과가 자리를 차지합니다: 큰 행렬을 곱할수록 결과를 쌓을 칸이 많이 필요합니다. 3.8에서 봅니다.
    3.8

    단점 극복을 위한 대안 기술

    1. 레지스터 상한 지정

    • 뜻: __launch_bounds__나 -maxrregcount로 스레드당 칸 수의 상한을 컴파일러에 알려 줍니다.
    • 해결하는 단점: 점유율을 원하는 수준으로 맞춥니다. 넘침이 생기지 않는지 함께 확인합니다.

    2.

    • 뜻: warp 안 스레드끼리 레지스터 값을 직접 주고받는 명령입니다.
    • 해결하는 단점: 값을 나누려고 Shared Memory를 거칠 필요가 없어집니다.

    3. warp마다 칸 수 바꾸기 (H100부터)

    • 뜻: 데이터를 옮기는 warp는 칸을 적게, 계산하는 warp는 많이 쓰도록 실행 중에 나눠 줍니다. setmaxnreg 명령이고, Warp Specialization과 함께 씁니다.
    • 해결하는 단점: 모든 스레드가 같은 칸 수를 받아 낭비되는 문제를 줄입니다.

    4. TMEM (데이터센터용 Blackwell부터)

    • 뜻: Tensor Core 결과를 레지스터 대신 담는 SM 안의 전용 공간입니다.
    • 해결하는 단점: Tensor Core 결과가 레지스터를 차지하는 문제를 없앱니다.

    PART 4

    L1 · L2 Cache

    여기까지가 프로그래머와 컴파일러가 정하는 공간이었습니다. 마지막으로 하드웨어가 알아서 관리하는 L1과 L2 캐시를 보겠습니다.

    4.1

    정의

    과 L2는 최근에 읽은 데이터를 칩 안에 잠시 남겨, VRAM까지 가는 횟수를 줄이는 하드웨어 캐시입니다.

    • L1: SM마다 하나씩 있는 작고 빠른 캐시입니다. Shared Memory와 같은 SRAM을 나눠 씁니다.
    • L2: 칩 전체에 하나 있고, 모든 SM이 함께 씁니다. Global Memory를 읽고 쓰는 모든 요청이 L2를 거칩니다.
    • H100 SXM의 L2는 50MB입니다.
    4.2

    등장 배경

    • 초기 GPU에는 그림용 텍스처 캐시 말고 범용 캐시가 거의 없었습니다.
    • 그래서 그래프 탐색처럼 주소가 불규칙한 계산은 매번 VRAM까지 다녀와야 했습니다.
    "그럼 CPU처럼 하드웨어가 알아서 채우는 범용 캐시를 두 단계로 두자!"그래서 2010년 Fermi에서 등장한 것이 바로 L1과 캐시입니다.
    • Fermi의 L2는 768KB였고, H100은 50MB입니다.

    작동 방식

    1. L1에서 찾기: 스레드가 Global Memory 주소를 읽으면 먼저 자기 SM의 L1을 봅니다. 있으면 바로 받습니다. 이걸 , 영어로 hit라고 합니다.
    2. L2에서 찾기: L1에 없으면 L2를 봅니다.
    3. VRAM에서 가져오기: L2에도 없으면 VRAM에서 가져오고, 오는 길에 L2와 L1에 남겨 둡니다.
    4. 밀어내기: 캐시가 차면 오래 안 쓴 데이터를 밀어내고 새 데이터를 넣습니다.
    Q. Shared Memory와 L1은 같은 공간인데, 무엇이 다른가요?

    물리적으로는 같은 SRAM입니다. 프로그래머가 __shared__로 무엇을 둘지 정하면 Shared Memory이고, 하드웨어가 최근 읽은 것을 알아서 남기면 L1입니다.

    4.5

    이점

    • 신경 쓰지 않아도 빨라집니다: 같은 데이터를 다시 읽으면 하드웨어가 알아서 칩 안에서 줍니다.
    • VRAM 대역폭을 아낍니다: L2에서 끝나는 요청은 VRAM까지 가지 않아서, 실제로 쓸 수 있는 대역폭이 늘어납니다.
    • SM끼리 데이터를 나눕니다: 여러 SM이 같은 가중치를 읽으면, 첫 SM이 가져온 것을 L2에서 나눠 받습니다.
    • 불규칙한 접근을 돕습니다: 그래프나 임베딩 조회처럼 Shared Memory로 미리 짜기 어려운 접근에 특히 도움이 됩니다.
    4.6

    부재 시 문제

    L1과 L2가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 모든 읽기가 VRAM까지 가서, 대역폭이 금방 바닥납니다.
    • 여러 SM이 같은 데이터를 각자 VRAM에서 따로 읽어 같은 일을 반복합니다.
    • 레지스터에서 넘친 값이 곧바로 VRAM으로 가서, 넘침의 손해가 훨씬 커집니다.
    4.7

    단점

    • 예측하기 어렵습니다: 데이터가 캐시 크기를 넘는 순간 적중률이 떨어지면서 성능이 갑자기 꺾입니다.
    • 스레드당 몫이 작습니다: 총량은 CPU 캐시와 비슷하거나 크지만, 동시에 도는 스레드가 수만 개라 한 스레드의 몫은 훨씬 작습니다.
    • L1은 SM끼리 값을 맞춰 주지 않습니다: 다른 SM이 쓴 값을 바로 봐야 하면 L2나 원자 연산을 써야 합니다.
    • 늘리기 비쌉니다: SRAM은 자리를 많이 차지하고, 공정이 미세해져도 잘 줄지 않습니다. 4.10에서 봅니다.
    4.8

    단점 극복을 위한 대안 기술

    1. Shared Memory로 직접 관리

    • 뜻: 반드시 재사용할 데이터는 캐시에 맡기지 않고 Shared Memory에 직접 둡니다. PART 2에서 본 방법입니다.
    • 해결하는 단점: 캐시가 예측하기 어려운 문제를 피합니다.

    2. L2 지속 영역 지정 (A100부터)

    • 뜻: 자주 쓰는 데이터 범위를 정해 주면, L2가 그 데이터를 오래 남깁니다. cudaAccessPolicyWindow로 정합니다.
    • 해결하는 단점: 중요한 데이터가 다른 데이터에 밀려나는 문제를 줄입니다.

    3. 타일링과

    • 뜻: 데이터를 캐시 크기에 맞게 잘라 처리하고, 여러 단계를 한 커널로 합쳐 중간 결과가 캐시 밖으로 나가지 않게 합니다.
    • 해결하는 단점: 데이터가 캐시를 넘쳐 성능이 꺾이는 문제를 줄입니다.

    4. L2 뒤의 큰 캐시

    • 뜻: L2와 VRAM 사이에 수백 MB의 캐시를 하나 더 둡니다. AMD의 Infinity Cache가 대표적입니다.
    • 해결하는 단점: L2가 작아서 VRAM까지 가는 요청을 한 번 더 걸러 냅니다.
    4.9

    4.10

    최신 트렌드

    1. L2가 계속 커집니다

    • H100은 50MB였고, Blackwell GB200은 칩 두 개를 합쳐 126MB입니다. NVIDIA의 Blackwell 튜닝 가이드에 나온 값입니다.
    • 작은 배치의 LLM 추론처럼 같은 데이터를 자주 다시 읽는 일에서 L2 적중률이 성능을 크게 좌우합니다.

    2. AMD는 L2 뒤에 큰 캐시를 둡니다

    • AMD MI355X는 계산 조각 8개에 L2를 4MB씩 두고, 그 뒤에 모두가 함께 쓰는 Infinity Cache 256MB를 둡니다.
    • NVIDIA와 다르게, 캐시를 한 단계 더 두어 HBM 접근을 줄이는 쪽입니다.

    3. 은 잘 줄지 않습니다

    • TSMC 3나노급 공정에서 SRAM 한 비트의 크기는 5나노와 거의 같습니다. 계산 회로는 계속 작아지는데, 캐시는 같은 용량에 비슷한 면적을 씁니다.
    • 그래서 캐시를 크게 늘릴수록 칩 값이 빠르게 오르고, 캐시를 별도 칩으로 만들어 쌓는 방식이 주목받습니다.
    꼭 알아 둘 것칩 안 메모리는 늘리기가 점점 비싸집니다. 그래서 같은 크기를 더 잘 쓰는 기술, 즉 Shared Memory 관리, L2 지정, 커널 퓨전이 함께 중요해집니다.

    여기까지가 GPU 메모리의 칸들이었습니다. 각 칸 사이를 데이터가 얼마나 빨리, 얼마나 많이 오가는지, 즉 대역폭과 지연은 6회차에서 다룹니다.
