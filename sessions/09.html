    9회차 · NVLink, NVSwitch, P2P, GPUDirect 계열

    지난 8회차에서는 CPU와 GPU 사이에서 데이터가 어떻게 움직이는지 봤습니다. 장치가 직접 데이터를 옮기는 DMA와, GPU 메모리를 바깥에 열어 보이는 창 BAR가 핵심이었습니다. 오늘은 GPU가 여러 장일 때, GPU끼리 어떻게 데이터를 주고받는지 보겠습니다.

    오늘은 네 가지를 봅니다. 첫째는 GPU끼리 직접 잇는 전용 고속 연결, 입니다. 둘째는 그 NVLink를 한곳에 모아 모든 GPU를 최고 속도로 잇는 스위치 칩, 입니다. 셋째는 CPU 메모리를 들르지 않고 GPU 메모리끼리 바로 주고받는 방식, 입니다. 넷째는 이 직접 통신을 네트워크 카드와 스토리지까지 넓힌 기술 묶음, 입니다.

    ※ 기준 제품은 5회차부터 써 온 NVIDIA SXM이고, 서버는 DGX H100입니다. DGX H100은 HGX H100 8-GPU 보드 위에 H100 SXM 8장과 NVSwitch 4개를 올리고, GPU마다 400Gb/s ConnectX-7 NIC을 하나씩, 모두 8개 붙입니다. 대역폭은 기준을 함께 적습니다. NVLink는 보통 양방향 합계로, PCIe와 NIC은 한 방향 기준으로 말합니다.

    PART 1

    NVLink

    먼저 GPU끼리 잇는 길부터 보겠습니다. 7회차에서 본 PCIe는 CPU와 GPU를 잇는 범용 길이었습니다. GPU가 여러 장이 되면, 이 길만으로는 GPU끼리 주고받는 데이터를 감당하기 어렵습니다.

    1.1

    정의

    는 NVIDIA GPU끼리, 또는 GPU와 CPU를 직접 잇는 NVIDIA 전용 고속 연결입니다.

    • 두 장치를 일대일로 잇는 점대점 연결이고, 링크 여러 개를 묶어 대역폭을 키웁니다.
    • 다른 GPU 메모리를 직접 읽고 쓰는 load와 store, 원자 연산까지 지원합니다.
    • 그래서 여러 GPU의 메모리를 하나처럼 쓰는 바탕이 됩니다.
    1.2

    등장 배경

    • 딥러닝 모델이 GPU 한 장의 메모리를 넘어서면서, 여러 GPU가 그래디언트와 활성값을 계속 주고받아야 했습니다.
    • 2014년 무렵 Gen3 x16은 한 방향 약 16GB/s였습니다. GPU의 계산 속도에 비해 턱없이 느렸습니다.
    "그럼 GPU끼리 따로 넓은 길을 깔자!"그래서 등장한 것이 바로 NVLink입니다.
    • 2016년 Pascal 세대 P100에서 NVLink 1세대가 처음 들어갔습니다.
    1.3

    구조

    1. 세대별 대역폭

    세대GPUGPU당 링크 수GPU당 대역폭, 양방향

    2. H100의 NVLink

    • H100 SXM은 NVLink 4 링크 18개를 가집니다. 링크 하나가 한 방향 25GB/s라서, 18개를 합치면 한 방향 450GB/s, 양방향 900GB/s입니다.
    • 7회차에서 본 PCIe Gen5 x16은 한 방향 약 64GB/s, 양방향 약 128GB/s입니다. 같은 양방향 기준으로 NVLink가 약 7배 넓습니다.

    3. 연결 형태

    • GPU가 2장에서 4장이면 브리지나 메시로 직접 잇습니다.
    • 8장 이상이면 NVSwitch를 거쳐 모든 GPU를 서로 잇습니다. PART 2에서 봅니다.
    • Grace Hopper와 Grace Blackwell은 CPU와 GPU 사이에도 를 씁니다. GH200에서 이 연결은 900GB/s이고, 8회차에서 봤습니다.
    Q. H100 NVLink 대역폭은 PCIe Gen5 x16의 대략 몇 배인가요?

    양방향 기준으로 900GB/s를 약 128GB/s로 나누면 약 7배입니다. 한 방향 기준으로 450GB/s와 약 64GB/s를 비교해도 같은 약 7배입니다.

    1.4

    작동 방식

    1. 인식: GPU 드라이버가 부팅할 때 NVLink 연결 구조를 알아냅니다. nvidia-smi topo -m을 실행하면 GPU 사이가 NV18처럼 표시됩니다. NVLink 18개로 이어졌다는 뜻입니다.
    2. 직접 접근: P2P가 켜지면, GPU A의 커널이 GPU B 메모리 주소를 직접 읽고 씁니다. PART 3에서 봅니다.
    3. 집단 통신: 같은 통신 라이브러리가 NVLink를 먼저 골라 AllReduce 같은 집단 통신을 합니다. 10회차에서 다룹니다.
    4. 전송: 데이터는 패킷으로 나뉘어 여러 링크에 나눠 실려 가고, CRC로 오류를 잡아 다시 보냅니다.
    1.5

    이점

    • 대역폭이 넓습니다: 같은 양방향 기준으로 PCIe Gen5 x16의 약 7배입니다. 그래서 레이어마다 통신하는 같은 방식이 가능해집니다.
    • 지연이 짧습니다: CPU와 PCIe 루트 컴플렉스를 거치지 않습니다.
    • 메모리를 묶어 씁니다: 여러 GPU 메모리를 하나의 큰 메모리처럼 씁니다. GB200 NVL72는 GPU 72장을 하나의 NVLink 영역으로 묶습니다.
    1.6

    부재 시 문제

    NVLink가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • GPU 8장 서버에서 GPU 사이 통신이 PCIe 스위치와 CPU를 거칩니다. 텐서 병렬은 사실상 어렵고, 데이터 병렬도 통신을 기다리는 시간이 늘어납니다. 분산 학습의 병렬화 방식은 17회차에서 다룹니다.
    • 70B 이상 모델을 여러 GPU로 추론하면, GPU 사이 활성값 교환이 느려져 토큰 생성 속도가 떨어집니다.
    1.7

    단점

    • NVIDIA 전용입니다: 다른 회사의 가속기와는 이을 수 없습니다. 데이터센터 GPU 위주이고, 소비자 GPU는 RTX 4090부터 NVLink가 빠졌습니다.
    • 거리가 짧습니다: 서버 안이나 랙 안을 잇습니다. 랙 사이는 나 Ethernet이 필요하고, 11회차에서 다룹니다.
    • 비용, 전력, 발열이 늘어납니다: 큰 NVSwitch 시스템은 랙 단위 액체 냉각이 필요합니다.
    Q. RTX 4090 여러 장으로는 NVLink를 못 쓰나요?

    RTX 4090부터 소비자 GPU에서 NVLink가 빠졌고, P2P도 막혀 있는 경우가 많습니다. 그래서 GPU 사이 통신이 CPU 메모리를 거치고, 여러 GPU로 학습하는 효율이 데이터센터 GPU보다 크게 떨어집니다.

    1.8

    단점 극복을 위한 대안 기술

    1. UALink

    • 뜻: Ultra Accelerator Link의 줄임말로, AMD, Intel, Google, Microsoft 등이 함께 만드는 가속기 사이 연결의 개방 표준입니다. 라고 부릅니다.
    • 해결하는 단점: 한 회사에 묶이는 문제를 풉니다.

    2. AMD Infinity Fabric

    • 뜻: MI300X 같은 AMD GPU끼리 잇는 연결입니다.
    • 해결하는 단점: NVIDIA가 아닌 GPU에서도 GPU 간 고속 연결을 씁니다.

    3. NVLink Fusion

    • 뜻: NVIDIA가 다른 회사의 CPU와 가속기에도 NVLink를 열어 주는 프로그램입니다.
    • 해결하는 단점: NVIDIA 전용이라는 제약을 일부 풉니다.

    4. PCIe Gen6와 CXL

    • 뜻: 범용 표준 연결의 대역폭을 키우고, CXL로 메모리를 일관되게 함께 씁니다.
    • 해결하는 단점: 표준 부품만으로 연결 폭을 넓힙니다.

    1.10

    최신 트렌드

    1. NVLink 6와 Rubin

    • 2026년 1월 CES에서 NVIDIA는 Vera Rubin 플랫폼을 공개했습니다. Rubin GPU의 NVLink 6는 GPU당 양방향 3.6TB/s로, H100의 4배입니다.
    • Vera Rubin NVL72는 GPU 72장을 모두 서로 잇고, 랙 전체 NVLink 대역폭은 260TB/s입니다. 출시는 2026년 하반기로 발표됐습니다.

    2. NVLink Fusion으로 문을 엽니다

    • 2025년 5월 Computex에서 NVIDIA는 을 발표했습니다. Fujitsu와 Qualcomm은 자기 CPU를 NVIDIA GPU와 잇겠다고 밝혔고, MediaTek, Marvell, Alchip은 맞춤 가속기 설계로 참여했습니다.
    • 2025년 12월에는 AWS가 다음 세대 Trainium4 칩에 NVLink Fusion을 쓰겠다고 발표했습니다.

    3. 개방 표준 UALink가 따라옵니다

    • 2025년 4월 UALink 200G 1.0 사양이 나왔습니다. 레인당 200Gb/s이고, 사양상 가속기 1,024개까지 한 묶음으로 잇습니다.
    • 2026년 4월에는 2.0 사양이 나와, 스위치 안에서 계산하는 In-Network Compute를 더했습니다.
    • 다만 1.0 칩은 2026년 하반기에 시험 단계에 들어가고, 제품은 2027년으로 예상됩니다.
    꼭 알아 둘 것GPU 간 연결은 세대마다 두 배씩 넓어지고 있고, NVIDIA 전용과 개방 표준이 함께 경쟁하는 구도가 됐습니다.
    PART 2

    NVSwitch

    여기까지가 GPU끼리 잇는 길, NVLink였습니다. 그런데 GPU가 8장을 넘으면 모든 쌍을 직접 이을 링크가 모자랍니다. 이제 그 길을 한곳에 모으는 NVSwitch로 넘어가겠습니다.

    2.1

    정의

    는 여러 GPU의 NVLink를 한곳에 모아, 모든 GPU가 다른 모든 GPU와 최대 대역폭으로 동시에 통신하게 하는 스위치 칩입니다.

    • NVLink 포트를 많이 가진 전용 칩이고, 어느 GPU 쌍이든 막힘 없이 잇는 non-blocking all-to-all 연결을 만듭니다.
    • 3세대부터는 스위치 안에서 합계를 계산하는 를 지원합니다. SHARP는 In-network reduction, 즉 네트워크 안에서 하는 합산입니다.
    2.2

    등장 배경

    • NVLink를 GPU끼리 직접 메시로 이으면, GPU가 늘수록 GPU 쌍마다 쓸 수 있는 링크가 줄어듭니다.
    • GPU 8장을 하이브리드 큐브 메시로 이은 구성에서는, 일부 GPU 쌍이 직접 이어지지 않았습니다.
    "그럼 가운데에 스위치를 두고, 모든 GPU를 거기 잇자!"그래서 등장한 것이 바로 NVSwitch입니다.
    • 2018년 DGX-2에서 V100 16장을 모두 서로 잇기 위해 1세대 NVSwitch가 처음 쓰였습니다.
    Q. NVLink만 있으면 NVSwitch는 왜 필요한가요?

    GPU 하나가 가진 링크 수가 정해져 있어서, GPU가 많아지면 모든 GPU를 서로 직접 이을 수 없습니다. NVSwitch가 가운데서 모든 링크를 받아 주면, 어느 GPU 쌍이든 최고 속도로 통신합니다.

    2.3

    구조

    1. 세대별 구성

    세대대표 시스템특징
    1세대DGX-2, V100 16장NVSwitch 12개로 GPU 16장을 모두 연결
    2세대DGX A100NVSwitch 6개, GPU 8장, GPU당 600GB/s
    3세대DGX H100NVSwitch 4개, NVLink SHARP, 외부 NVLink Switch로 최대 GPU 256장 연결 가능
    4세대GB200 NVL72스위치 트레이 9개, 트레이마다 칩 2개, GPU 72장이 하나의 NVLink 영역
    NVLink 6 SwitchVera Rubin NVL72트레이마다 칩 4개, 랙 전체 260TB/s

    2. DGX H100 안의 연결

    • H100 한 장의 NVLink 18개는 NVSwitch 4개에 5개, 4개, 4개, 5개로 나뉘어 연결됩니다.
    • 그래서 어느 GPU 쌍이든 스위치를 한 번만 거쳐 양방향 900GB/s로 통신합니다.

    3. Fabric Manager

    • NVSwitch 시스템에서 GPU와 스위치 사이 길을 설정하는 서비스가 입니다. 서비스 이름은 nvidia-fabricmanager입니다.
    • 이 서비스가 없으면 GPU 사이 NVLink 통신이 되지 않습니다.
    2.4

    작동 방식

    1. 연결: GPU마다 NVLink 링크가 여러 NVSwitch에 고르게 나뉘어 연결됩니다.
    2. 길 설정: 부팅할 때 Fabric Manager가 스위치의 라우팅 테이블을 설정합니다.
    3. 전달: GPU A에서 GPU B로 가는 데이터는 스위치를 한 번 거쳐 갑니다.
    4. 스위치 안 합산: NVLink SHARP를 쓰면, 때 GPU들이 데이터를 스위치로 보내고 스위치가 합산해 결과를 다시 돌려줍니다. GPU가 보내야 하는 데이터 양이 크게 줄어듭니다. 자세한 계산은 10회차에서 봅니다.
    2.5

    이점

    • 어느 쌍이든 같은 속도입니다: GPU 8장에서 72장까지, 어느 GPU 쌍이든 대역폭이 같습니다. 그래서 통신 방식과 상관없이 성능을 예측할 수 있습니다.
    • 집단 통신이 빨라집니다: 스위치 안에서 합산하면 GPU가 주고받는 데이터가 줄어듭니다.
    • 큰 하나의 GPU처럼 씁니다: 랙 하나를 하나의 NVLink 영역으로 묶어, 아주 큰 모델을 한 덩어리로 돌립니다.
    2.6

    부재 시 문제

    NVSwitch가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • GPU가 늘면 일부 GPU 쌍은 다른 GPU를 거쳐 통신합니다. 쌍마다 대역폭이 달라지고, 텐서 병렬 그룹을 어디에 둘지 제약이 생깁니다.
    • Kubernetes에서 GPU 일부만 나눠 줄 때, 어떤 GPU 조합이 빠른지까지 신경 써야 합니다. 토폴로지를 고려한 배치는 12회차와 15회차에서 다룹니다.
    2.7

    단점

    • 비용, 전력, 발열이 큽니다: NVL72 랙은 액체 냉각이 필수입니다.
    • Fabric Manager에 기댑니다: 서비스가 죽거나 드라이버와 버전이 다르면 GPU 초기화가 실패합니다. 운영 장애의 단골 원인입니다.
    • NVIDIA 전용이고, 랙을 넘지 못합니다: 랙 바깥은 InfiniBand나 Ethernet으로 바꿔 타야 합니다.
    Q. NVSwitch 서버에서 GPU 간 통신이 안 되면 무엇부터 보나요?

    nvidia-fabricmanager 서비스가 떠 있는지, 그리고 드라이버와 정확히 같은 버전인지 먼저 봅니다. Fabric Manager가 안 뜨면 CUDA 초기화 실패, 예를 들어 system not yet initialized 오류나 NCCL 통신 실패가 납니다.

    2.8

    단점 극복을 위한 대안 기술

    1. UALink Switch

    • 뜻: UALink 표준을 따르는 가속기용 스위치입니다.
    • 해결하는 단점: NVIDIA 전용이라는 제약을 풉니다.

    2. PCIe 스위치 기반 서버

    • 뜻: GPU를 PCIe 스위치로 잇는 값싼 구성입니다.
    • 해결하는 단점: 비용을 낮춥니다. 대신 대역폭은 크게 낮습니다.

    3. Scale-out 네트워크

    • 뜻: 랙 사이는 InfiniBand나 Ethernet과 로 잇습니다. 11회차와 12회차에서 다룹니다.
    • 해결하는 단점: 랙 경계를 넘어 GPU를 늘립니다.
    2.9

    대안과의 비교

    구성GPU 수GPU 간 대역폭비용용도
    NVSwitch, HGX 8-GPU8균일, 최고높음큰 모델 학습과 추론의 표준
    랙72균일, 최고매우 높음초대형 모델, MoE
    NVLink 브리지2~4브리지로 이은 쌍만 빠름중간워크스테이션, 작은 서버

    2.10

    최신 트렌드

    1. NVLink 6 Switch

    • Vera Rubin NVL72의 스위치 트레이에는 NVLink 6 스위치 칩이 4개씩 들어갑니다. 트레이 하나의 대역폭은 28.8TB/s입니다.
    • 트레이마다 FP8 기준 14.4 TFLOPS의 스위치 안 계산 능력이 있어, 집단 통신의 합산을 스위치가 맡습니다.

    2. 스위치 안 계산이 개방 표준으로도 갑니다

    • 2026년 4월 나온 UALink 2.0 사양은 In-Network Compute를 넣었습니다. NVLink SHARP처럼 스위치 안에서 계산하는 기능이 개방 표준에도 들어간 것입니다.
    꼭 알아 둘 것스위치는 데이터를 나르기만 하는 장치에서, 합산까지 맡는 계산 장치로 바뀌고 있습니다.
    PART 3

    P2P (Peer-to-Peer)

    여기까지가 GPU를 잇는 하드웨어, NVLink와 NVSwitch였습니다. 이제 그 길 위에서 GPU끼리 실제로 데이터를 주고받는 방식, P2P로 넘어가겠습니다.

    3.1

    정의

    , Peer-to-Peer는 같은 서버 안의 GPU가 CPU 메모리를 거치지 않고 다른 GPU의 메모리로 직접 복사하거나 접근하는 기능입니다.

    • CUDA의 GPU 간 직접 통신 기능이고, GPUDirect P2P라고도 부릅니다. 길은 NVLink이거나, 같은 PCIe 스위치 아래의 PCIe입니다.
    • 형태는 두 가지입니다. 하나는 P2P 복사로, cudaMemcpyPeer를 씁니다. 다른 하나는 P2P 접근으로, 커널이 다른 GPU 메모리를 직접 읽고 씁니다.
    3.2

    등장 배경

    • P2P가 없으면 GPU 0의 데이터를 CPU 메모리에 한 번 내린 뒤, 다시 GPU 1로 올려야 합니다.
    • 복사가 두 번이라 지연이 두 배가 되고, CPU 메모리 대역폭도 낭비됩니다.
    "그럼 CPU 메모리에 들르지 말고, GPU끼리 바로 주고받자!"그래서 등장한 것이 바로 P2P입니다.
    • 2011년 CUDA 4.0에서 GPUDirect P2P와 , 즉 통합 가상 주소가 함께 나왔습니다.
    3.3

    구조

    1. UVA

    • UVA, Unified Virtual Addressing은 CPU와 모든 GPU의 메모리를 하나의 가상 주소 공간에 놓는 방식입니다.
    • 그래서 주소만 보고도 어느 GPU의 메모리인지 알 수 있습니다.

    2. GPU 사이 경로

    은 GPU 사이 경로를 아래 표기로 보여 줍니다.

    표기뜻P2P 성능
    NV#NVLink # 개로 연결가장 좋음
    PIXPCIe 스위치 하나를 거침좋음
    PXBPCIe 스위치 여러 개를 거침, CPU는 안 거침보통
    PHBCPU의 PCIe 호스트 브리지를 거침낮음
    NODE같은 NUMA 노드 안에서 호스트 브리지 사이를 건넘낮음
    SYSCPU 소켓 사이 링크, UPI를 건넘가장 낮거나 불가
    • SYS는 8회차에서 본, 소켓 사이를 건너는 가장 느린 경로입니다.
    Q. NV18, PIX, SYS는 각각 무슨 뜻인가요?

    NV18은 NVLink 18개로 이어졌다는 뜻입니다. PIX는 PCIe 스위치 하나만 거친다는 뜻입니다. SYS는 CPU 소켓 사이 링크를 건넌다는 뜻이고, 가장 느린 경로입니다.

    3.4

    작동 방식

    1. 가능한지 확인: cudaDeviceCanAccessPeer로 두 GPU 사이 P2P가 되는지 봅니다.
    2. 켜기: cudaDeviceEnablePeerAccess로 P2P 접근을 켭니다.
    3. 복사: cudaMemcpyPeer가 CPU 메모리를 거치지 않고 한 번에 복사합니다.
    int can; cudaDeviceCanAccessPeer(&can, 0, 1);  // GPU0에서 GPU1로 P2P 가능한가
cudaSetDevice(0); cudaDeviceEnablePeerAccess(1, 0);
cudaMemcpyPeer(dst_on_gpu1, 1, src_on_gpu0, 0, bytes);  // CPU 메모리를 거치지 않고 복사
    • PyTorch에서는 tensor.to("cuda:1")이 P2P가 되면 알아서 직접 복사합니다.
    • NCCL은 P2P가 되는지 살펴서 NVLink, PCIe P2P, CPU 공유 메모리인 SHM 순서로 길을 고릅니다.
    Q. 학습이 느린데 P2P 문제인지 어떻게 아나요?

    NCCL_DEBUG=INFO로 실행해 로그의 경로가 P2P나 NVLS인지, SHM인지 봅니다. SHM이면 CPU 메모리를 거치는 느린 길입니다. CUDA 샘플 p2pBandwidthLatencyTest로 GPU 쌍마다 대역폭을 재 볼 수도 있습니다.

    3.5

    이점

    • 복사가 한 번으로 줄어듭니다: 지연과 CPU 부하가 함께 줄어듭니다.
    • CPU 메모리를 아낍니다: GPU 사이 데이터가 CPU 메모리 대역폭을 쓰지 않습니다.
    • 여러 GPU에 걸친 커널을 짤 수 있습니다: 커널이 다른 GPU 메모리를 직접 읽고 쓰니, 텐서 병렬 통신을 커널 안에서 최적화할 수 있습니다.
    3.6

    부재 시 문제

    P2P가 안 된다고 가정해 보면, 이런 문제가 생깁니다.

    • 모든 GPU 사이 전송이 CPU 메모리를 거칩니다. 대역폭이 크게 줄고, GPU를 늘려도 학습 속도가 잘 늘지 않습니다.
    • NCCL이 느린 SHM 경로로 떨어져, AllReduce 시간이 늘어납니다.
    3.7

    단점

    • PCIe P2P는 연결 구조에 달려 있습니다: CPU 소켓을 넘는 SYS 경로에서는 느리거나 아예 안 됩니다.
    • 가상화 설정이 길을 돌립니다: IOMMU나 설정이 P2P 데이터를 CPU 루트 컴플렉스로 우회시켜, 느려지거나 멈출 수 있습니다. ACS는 PCIe 스위치에서 장치끼리 바로 오가는 데이터를 막고 위로 올려 보내는 보안 기능입니다.
    • 소비자 GPU는 막혀 있는 경우가 많습니다: 드라이버에서 P2P를 꺼 둡니다.
    3.8

    단점 극복을 위한 대안 기술

    1. NVLink와 NVSwitch

    • 뜻: PCIe 대신 NVLink로 P2P를 합니다.
    • 해결하는 단점: PCIe 연결 구조의 제약이 사라집니다.

    2. BIOS와 커널 설정

    • 뜻: 베어메탈 서버에서는 ACS를 끄고, IOMMU를 passthrough 모드로 둡니다.
    • 해결하는 단점: P2P 데이터가 CPU 쪽으로 돌아가는 일을 막습니다.

    3. CUDA IPC와 VMM API

    • 뜻: 와 VMM은 서로 다른 프로세스가 GPU 메모리를 함께 쓰게 합니다. VMM은 Virtual Memory Management, 즉 GPU 가상 메모리 관리 API입니다.
    • 해결하는 단점: GPU마다 프로세스가 따로 떠 있어도 P2P로 데이터를 나눕니다.
    3.9

    대안과의 비교

    방식복사 횟수CPU 메모리 사용성능
    CPU 경유, staging2예낮음
    PCIe P2P1아니오중간, 연결 구조에 따라 다름
    NVLink P2P1아니오가장 좋음
    꼭 알아 둘 것P2P가 되는지는 GPU 사이 경로가 정합니다. 느리면 먼저 nvidia-smi topo -m으로 경로부터 봅니다.
    3.10

    최신 트렌드

    1. 커널 안에서 다른 GPU 메모리를 직접 다룹니다

    • NCCL 2.28은 Device API를 내놨습니다. GPU 커널 안에서 직접 통신을 부르는 방식입니다.
    • 이 가운데 LSA는 NVLink로 이어진 다른 GPU 메모리를 커널이 직접 읽고 쓰는 방식이고, Multimem은 NVLink SHARP를 쓰는 방식입니다.
    • 이때 GPU마다 같은 모양으로 등록한 메모리, 즉 를 씁니다. 자세한 내용은 10회차에서 다룹니다.

    2. P2P가 되는 범위가 랙 전체로 넓어집니다

    • NVL72 같은 랙 단위 NVLink 영역에서는 GPU 72장이 서로 NVLink로 이어집니다.
    • 예전에는 P2P가 서버 한 대 안의 이야기였지만, 이제는 랙 하나 전체가 P2P 범위가 됩니다.
    꼭 알아 둘 것P2P는 복사 명령에서, 커널이 다른 GPU 메모리를 자기 메모리처럼 다루는 방식으로 넓어지고 있습니다.
    PART 4

    GPUDirect 계열

    여기까지가 같은 서버 안의 GPU끼리 주고받는 방식, P2P였습니다. 마지막으로, 이 직접 통신을 다른 서버의 GPU와 스토리지까지 넓힌 GPUDirect 계열로 넘어가겠습니다.

    4.1

    정의

    는 GPU 메모리와 다른 장치 사이 데이터 전송에서 CPU와 CPU 메모리를 빼는 NVIDIA 기술 묶음입니다.

    기술도입무엇을 직접 잇나
    GPUDirect Shared Memory2010GPU와 NIC 드라이버가 같은 고정 호스트 버퍼를 함께 써서 복사를 한 번 줄임
    GPUDirect P2P2011같은 서버의 GPU와 GPU, PART 3
    GPUDirect RDMA2013, KeplerGPU 메모리와 NIC, 그리고 다른 서버
    GPUDirect Storage, GDS2021, 1.0NVMe나 원격 스토리지와 GPU 메모리
    GPUDirect Async-GPU가 직접 NIC 작업을 시작, CPU가 통신 제어에서 빠짐
    4.2

    등장 배경

    • 서버 사이 학습에서 예전 경로는 GPU, CPU 메모리, NIC, 네트워크, 상대 NIC, 상대 CPU 메모리, 상대 GPU 순서였습니다. 중간에 복사가 여러 번 들어가고, CPU가 매번 끼어듭니다.
    • 데이터 로딩도 스토리지에서 CPU 메모리의 임시 버퍼, 즉 를 거쳐 GPU로 갔습니다. CPU 메모리 대역폭과 CPU 사용률이 병목이 됐습니다.
    • GPU가 빨라질수록 CPU를 거치는 비용이 상대적으로 커졌습니다.
    "그럼 CPU 메모리를 건너뛰고, 장치끼리 GPU 메모리를 바로 읽고 쓰게 하자!"그래서 등장한 것이 바로 GPUDirect RDMA와 GPUDirect Storage입니다.
    • GPUDirect RDMA는 Kepler 세대부터, GPUDirect Storage는 2021년 1.0부터 쓰였습니다.
    4.3

    구조

    1. GPUDirect RDMA

    • NIC이 PCIe를 거쳐 GPU 메모리에 직접 합니다. 이때 NIC이 들어가는 주소가 8회차에서 본 BAR1입니다.
    • GPU 메모리를 NIC에 등록하려면 커널 모듈 nvidia-peermem이나, Linux 표준 방식인 DMA-BUF를 씁니다.

    2. GPUDirect Storage

    • 는 cuFile API와 nvidia-fs 커널 드라이버로, NVMe나 NVMe-oF, 병렬 파일 시스템에서 GPU 메모리로 직접 DMA합니다.

    3. 배치

    • GPU와 NIC이 같은 PCIe 스위치 아래 있어야 가장 빠릅니다.
    • 그래서 DGX H100은 GPU마다 400Gb/s ConnectX-7 NIC을 하나씩 짝지어, 모두 8개를 둡니다. 서버 한 대의 바깥 대역폭은 3.2Tb/s입니다.
    • 400Gb/s는 한 방향 초당 50GB입니다. PCIe Gen5 x16의 한 방향 약 64GB/s 안에 들어가는 값입니다.
    Q. GPUDirect RDMA에 필요한 커널 모듈은 무엇인가요?

    nvidia-peermem입니다. 최신 드라이버와 커널에서는 이 모듈 대신 DMA-BUF를 쓸 수 있습니다.

    4.4

    작동 방식

    GPUDirect RDMA를 따라가 보겠습니다.

    1. 버퍼 전달: 학습 프레임워크가 GPU 메모리 버퍼를 NCCL에 넘깁니다.
    2. 메모리 등록: NCCL이 nvidia-peermem이나 로 그 GPU 메모리를 NIC에 등록합니다.
    3. 전송: NIC이 GPU 메모리에서 직접 읽어 네트워크로 보내고, 상대 NIC은 상대 GPU 메모리에 직접 씁니다.
    4. CPU의 역할: CPU는 제어만 하고 데이터 경로에서는 빠집니다. GPUDirect Async는 그 제어까지 GPU가 맡습니다.

    자세한 RDMA 원리는 11회차에서 다룹니다.

    Q. GPUDirect RDMA가 실제로 켜졌는지 어떻게 확인하나요?

    NCCL_DEBUG=INFO 로그에서 GDR이나 GPU Direct RDMA Enabled 문구를 찾습니다. 서버에서는 lsmod | grep nvidia_peermem으로 모듈이 올라왔는지 봅니다.

    4.5

    이점

    • 서버 사이 통신이 빨라집니다: 지연이 줄고, 대역폭이 늘고, CPU 사용률이 줄어듭니다.
    • 데이터와 체크포인트가 빨리 오갑니다: GDS는 데이터 로딩과 체크포인트 저장, 복원을 빠르게 합니다. 체크포인트는 19회차에서 다룹니다.
    • 서버를 늘린 만큼 빨라집니다: 여러 서버 학습의 확장 효율이 좋아집니다.
    Q. GPUDirect Storage가 특히 효과적인 작업은 무엇인가요?

    대용량 데이터셋 로딩과, 큰 체크포인트의 저장과 복원입니다.

    4.6

    부재 시 문제

    GPUDirect가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 서버 사이 AllReduce가 CPU 메모리 복사로 느려집니다. 서버를 늘려도 학습 속도가 그만큼 늘지 않습니다.
    • 큰 데이터셋과 체크포인트를 불러올 때 CPU가 병목이 되어, GPU가 놀며 기다립니다.
    4.7

    단점

    • 조건이 까다롭습니다: 지원 NIC, 커널 모듈, 드라이버 버전, PCIe 연결 구조가 모두 맞아야 합니다.
    • 컨테이너 환경이 복잡합니다: Kubernetes에서 RDMA 장치를 Pod에 보여 주고 권한을 주는 설정이 복잡합니다.
    • GDS는 워크로드를 탑니다: 지원 파일 시스템과 정렬 조건이 있고, 작은 파일이 많으면 이득이 적습니다.
    Q. GPU와 NIC의 위치가 왜 중요한가요?

    GPU와 NIC이 같은 PCIe 스위치 아래 있으면 데이터가 스위치에서 바로 오갑니다. 하지만 서로 다른 CPU 소켓에 있으면 소켓 사이 링크인 UPI를 건너, 대역폭과 지연이 크게 나빠집니다. 8회차에서 본 이야기입니다.

    4.8

    단점 극복을 위한 대안 기술

    1. NVIDIA Network Operator와 GPU Operator

    • 뜻: Kubernetes에서 RDMA 드라이버, nvidia-peermem, SR-IOV 장치 플러그인을 자동으로 깔아 줍니다. 는 13회차에서 다룹니다.
    • 해결하는 단점: 컨테이너 환경의 복잡한 설정을 줄입니다.

    2. DMA-BUF

    • 뜻: Linux 표준 방식으로, 따로 peermem 모듈 없이 GPU 메모리를 NIC과 함께 씁니다.
    • 해결하는 단점: 커널 모듈과 드라이버 버전을 맞추는 부담을 줄입니다.

    3. GPU 데이터 로더와 프리페치

    • 뜻: GDS를 못 쓰는 환경에서는 DALI 같은 GPU 데이터 로더, 페이지 캐시, 미리 읽기로 대신합니다.
    • 해결하는 단점: 스토리지 경로에서 생기는 CPU 병목을 줄입니다.

    4.10

    최신 트렌드

    1. 서버 바깥 대역폭이 GPU당 1.6Tb/s로 갑니다

    • Vera Rubin 플랫폼의 ConnectX-9 SuperNIC은 GPU당 1.6Tb/s를 냅니다. 800Gb/s 포트 두 개 분량입니다.
    • DGX H100의 GPU당 400Gb/s와 비교하면 4배입니다.

    2. GPU가 직접 네트워크 통신을 시작합니다

    • NCCL 2.28.7부터 , GPU-Initiated Networking이 들어갔습니다. GPU 커널이 CPU를 거치지 않고 InfiniBand나 RoCE로 원격 메모리 쓰기를 직접 시작합니다.
    • 2025년 11월 NVIDIA는 이 구조를 arXiv 논문 2511.15076으로 공개했습니다. GPUDirect Async가 노리던 방향이 실제 라이브러리에 들어온 것입니다.

    3. GPU 메모리를 내보내는 방식이 표준이 되고, 열립니다

    • NVIDIA GPU Operator 문서는 2025년 v25.3부터 GPUDirect RDMA에 DMA-BUF를 권장합니다. 8회차에서 봤습니다.
    • 2026년 8월에는 GPUDirect Storage의 API인 cuFile과 스토리지 스택을 NVIDIA가 오픈소스로 공개했다는 보도가 나왔습니다.
    꼭 알아 둘 것GPUDirect는 데이터 경로에서 CPU를 뺀 데 이어, 이제 통신을 시작하는 제어에서도 CPU를 빼고 있습니다.

    여기까지가 9회차였습니다. 오늘은 GPU끼리 잇는 하드웨어 NVLink와 NVSwitch, 그 위에서 직접 주고받는 P2P, 그리고 네트워크와 스토리지까지 넓힌 GPUDirect를 봤습니다. 다음 10회차에서는 이 길 위에서 여러 GPU가 데이터를 어떤 순서로 주고받는지, NCCL과 집단 통신을 봅니다. AllReduce, AllGather, ReduceScatter입니다.
