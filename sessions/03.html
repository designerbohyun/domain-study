    3회차 · Kernel, Thread, Block, Grid, Warp

    지난 2회차에서는 SM 안을 들여다봤습니다. 블록이 SM에 배정되고, Warp Scheduler가 warp를 골라 실행한다는 것까지 봤습니다. 오늘은 그 일감이 프로그램 쪽에서 어떻게 쪼개지는지 보겠습니다. 2회차 1.4 표에서 이름만 보고 지나간 커널, 블록, warp, 스레드가 오늘의 주인공입니다.

    오늘의 예시: 숫자 100만 개에 2 곱하기

    오늘은 예시 하나를 끝까지 들고 가겠습니다. 숫자 100만 개가 든 배열이 있고, 모든 숫자에 2를 곱하려고 합니다.

    • CPU는 반복문으로 숫자를 하나씩, 100만 번 곱합니다.
    • GPU는 숫자 하나마다 작은 실행 흐름, 즉 스레드를 하나씩 붙여서 한꺼번에 곱합니다.
    • 오늘 볼 다섯 단어는 이 일을 나누는 단위입니다.

    PART 1

    Kernel (커널)

    가장 바깥 단위인 커널부터 보겠습니다.

    1.1

    정의

    은 CPU가 실행을 지시하고, GPU의 수많은 스레드가 똑같이 실행하는 함수입니다.

    • 코드에는 숫자 하나에 할 일만 적습니다. 오늘 예시에서는 "내 숫자에 2를 곱한다" 한 줄입니다.
    • 실행하면 수천에서 수백만 개의 스레드가 이 코드를 각자 다른 숫자에 실행합니다.
    • CUDA C++에서는 함수 앞에 __global__을 붙여 커널로 만듭니다.
    Q. 기초 · 함수는 무엇인가요?

    입력을 받아 정해진 일을 하는 코드 묶음입니다. 한 번 써 두면 이름만 불러서 몇 번이고 실행할 수 있습니다. 운영체제의 커널과는 이름만 같습니다.

    Q. 이런 실행 방식에 이름이 있나요?

    프로그램 하나를 데이터 여러 개에 동시에 실행하는 방식을 라고 부릅니다. Single Program, Multiple Data의 줄임말입니다.

    1.2

    등장 배경

    • 이전에도 GPU는 계산이 빨랐지만, 그림을 그리는 용도로만 쓸 수 있었습니다.
    • 그래서 계산을 그림 그리기로 꾸며서 시켰습니다. 숫자는 이미지에 담아 넣고, 결과도 그림으로 받았습니다.
    • 계산은 셰이더, 즉 픽셀마다 실행되는 작은 그래픽 프로그램이 맡았습니다.
    • "점 하나마다 같은 프로그램을 실행한다"는 발상은 좋았지만, 그래픽을 모르는 사람은 쓰기 어려웠습니다.
    "그럼 원소마다 실행되는 함수를, 그래픽과 상관없이 C 코드로 쓰게 하자!" 그래서 2006년 CUDA 발표와 함께 등장한 것이 바로 커널입니다.
    • 2007년 첫 CUDA 툴킷이 나오면서, GPU에 보내는 작업 단위가 함수 형태로 정해졌습니다.
    • 1회차에서 본 배열 더하기 코드가 바로 커널입니다.
    1.3

    구조

    커널은 세 가지로 이루어집니다. 커널이라는 표시, 실행할 때 적는 크기, 그리고 지시가 GPU까지 가는 길입니다.

    1. 함수 지정자

    함수 앞에 붙이는 표시입니다. 누가 부르고 어디서 실행되는지를 정합니다. 오늘 보는 것은 __global__, 즉 커널입니다.

    지정자누가 부르나어디서 실행되나
    __global__CPUGPU (이것이 커널)
    __device__GPU 안의 다른 함수GPU
    __host__CPUCPU (아무것도 안 붙인 함수와 같음)

    2. 실행 구성

    커널을 부를 때는 꺾쇠 세 개 안에 실행 구성을 적습니다.

    kernel<<<그리드 크기, 블록 크기, 동적 Shared Memory, 스트림>>>(인자);
    • 앞의 두 값은 꼭 적습니다. 블록을 몇 개 만들지, 블록마다 스레드를 몇 개 둘지입니다.
    • 오늘 예시라면 scale<<<3907, 256>>>입니다. 블록 3,907개를 만들고, 블록마다 스레드 256개를 둡니다.
    • 뒤의 두 값은 생략할 수 있습니다.

    3. 실행 경로

    CPU의 지시는 네 단계를 거쳐 SM에 닿습니다.

    단계하는 일
    CPU커널 실행을 지시
    지시를 순서대로 쌓아 두는 대기열
    GPU 전체에서 블록을 SM에 나눠 주는 장치
    SM배정받은 블록을 실행
    Q. 기초 · 스트림은 무엇인가요?

    GPU에 보낼 작업을 쌓아 두는 대기열입니다. 같은 스트림에 넣은 작업은 순서대로 실행되고, 다른 스트림끼리는 동시에 실행될 수 있습니다. 데이터 복사와 계산을 다른 스트림에 넣어 겹치게 하는 데 많이 씁니다.

    1.4

    작동 방식

    오늘 예시를 코드로 쓰면 이렇습니다.

    __global__ void scale(float* x, float a, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 내가 맡을 숫자의 번호 (2.4에서 봄)
    if (i < n) x[i] = a * x[i];                     // 내 숫자에 a를 곱함
}
scale<<<(n + 255) / 256, 256>>>(d_x, 2.0f, n);  // n = 1,000,000. CPU는 기다리지 않고 바로 다음 줄로
cudaDeviceSynchronize();                         // GPU 작업이 끝날 때까지 대기
    1. 실행 지시: CPU가 커널 실행을 지시합니다. CPU는 끝나기를 기다리지 않고 바로 다음 줄로 넘어갑니다. 이걸 비동기 실행이라고 합니다.
    2. 대기열: 지시는 스트림에 쌓입니다. 같은 스트림의 커널은 순서대로, 다른 스트림의 커널은 동시에 실행될 수 있습니다.
    3. 블록 배정: GigaThread Engine이 블록 3,907개를 빈 SM에 나눠 줍니다. 2회차 1.4에서 본 블록 배정이 바로 이 부분입니다.
    4. 결과: 커널이 끝나면 결과는 VRAM에 남습니다. CPU가 결과를 쓰려면 cudaDeviceSynchronize()로 기다리거나 복사 명령을 내립니다.
    Q. 왜 커널 실행을 비동기로 하나요?

    CPU가 커널마다 끝나기를 기다리면, 그동안 CPU가 놀고 다음 지시도 늦어집니다. 다음 지시가 늦으면 GPU도 놉니다. 지시를 미리 쌓아 두면 GPU는 쉬지 않고 이어서 실행하고, CPU는 그동안 다음 데이터를 준비합니다.

    1.5

    이점

    • 스레드 하나 관점으로 씁니다: 수백만 개 병렬 실행을 함수 하나로 표현합니다. 오늘 예시의 계산도 코드 한 줄입니다.
    • GPU가 바뀌어도 그대로 돕니다: 같은 커널이 SM 24개인 RTX 4060에서도, 132개인 H100에서도 수정 없이 돕니다.
    • CPU와 겹쳐 일합니다: 비동기 실행이라 CPU는 그동안 다음 일을 준비합니다.
    1.6

    부재 시 문제

    커널이라는 단위가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • CPU가 숫자마다 반복문을 돌거나, CUDA 이전처럼 그래픽 기능으로 돌아가야 합니다.
    • GPU에 무엇을 시켰고 언제 끝났는지 다룰 단위가 없어, 작업 순서를 관리하기 어렵습니다.
    1.7

    단점

    • 실행할 때마다 비용이 듭니다: 커널 한 번을 띄우는 데 수 마이크로초가 걸립니다. 작은 커널을 수천 번 실행하면, GPU의 계산보다 CPU가 지시하는 속도가 더 느려집니다. LLM이 답을 토큰 하나씩 만들어 내는 단계가 대표적입니다.
    • 커널 사이 데이터는 VRAM을 거칩니다: 커널 A가 결과를 VRAM에 쓰고, 커널 B가 다시 읽습니다. 메모리를 오가는 시간이 낭비됩니다. 1.8의 그림에서 봅니다.
    • 디버깅이 어렵습니다: 수천 개 스레드가 동시에 돌아서, 어디서 틀렸는지 찾기 어렵습니다.
    Q. 기초 · 마이크로초는 얼마나 짧은 시간인가요?

    100만 분의 1초입니다. 사람에게는 아주 짧지만, GPU는 그동안 계산을 수천 번 할 수 있습니다. 계산 자체가 이보다 짧으면, 띄우는 비용이 계산보다 커집니다.

    Q. GPU-Util은 높은데 왜 느릴 수 있나요?

    2회차 4.9에서 본 것처럼 은 커널이 하나라도 돈 시간의 비율입니다. 작은 커널이 연달아 돌면 값은 높게 나오지만, 커널마다 GPU 일부만 쓰거나 커널 사이에 빈 구간이 생깁니다. Nsight Systems라는 도구의 타임라인으로 커널 사이의 빈 구간을 확인합니다.

    1.8

    단점 극복을 위한 대안 기술

    1. 커널 퓨전

    • 뜻: 여러 연산을 커널 하나로 합칩니다. 2회차 2.8에서 본 으로, torch.compile, Triton, FlashAttention이 대표 예입니다.
    • 해결하는 단점: 실행 횟수와 VRAM 왕복을 함께 줄입니다.

    2. CUDA Graphs

    • 뜻: 는 커널 실행 순서를 한 번 기록해 두고, 다음부터는 기록을 통째로 한 번에 실행합니다.
    • 해결하는 단점: 실행 비용을 커널마다 내지 않아도 됩니다.

    3. Persistent Kernel

    • 뜻: 은 커널을 한 번만 띄워 두고, 그 안에서 다음 일을 계속 가져와 처리합니다. 모델 전체를 커널 하나로 돌리는 Megakernel도 여기에 속합니다.
    • 해결하는 단점: 실행 비용과 커널 사이 공백을 거의 없앱니다. 4.8에서 다시 봅니다.

    4. 타일 단위 작성 도구

    • 뜻: , cuTile Python처럼 스레드 대신 타일 단위로 커널을 씁니다. 타일은 데이터를 바둑판처럼 나눈 조각입니다.
    • 해결하는 단점: 커널을 짜고 디버깅하는 부담을 줄입니다.

    1.10

    최신 트렌드

    1. 커널을 타일 단위로 씁니다: CUDA Tile

    • 2025년 12월 CUDA 13.1에서 이 나왔습니다. 스레드가 아니라 타일 단위로 커널을 쓰는 NVIDIA 공식 방식입니다.
    • Python용 cuTile Python이 먼저 나왔고, 2026년 CUDA 13.3에서 C++로도 쓸 수 있게 됐습니다.
    • 처음에는 Blackwell만 지원했지만, 2026년에 Ampere, Ada, Hopper까지 넓어졌습니다.
    • Tensor Core처럼 다루기 어려운 장치를 쓰는 일은 컴파일러가 맡습니다.

    2. 모델 전체를 커널 하나로: Megakernel

    • Mirage Persistent Kernel, 줄여서 MPK는 모델 전체를 커널 하나로 바꿔 주는 컴파일러입니다. 2026년 OSDI 학회에 실렸습니다. 이런 방식을 이라고 부릅니다.
    • 연산마다 커널을 띄우는 방식보다 추론 지연을 최대 1.7배 줄였다고 보고했습니다. A100, H100, B200에서 평가했습니다.
    • 효과는 한 번에 들어오는 요청이 적은 토큰 생성 단계에서 가장 큽니다.

    3. AI가 커널을 씁니다

    LLM으로 CUDA와 Triton 커널을 자동으로 만들고 다듬는 시도가 늘고 있습니다. KernelBench 같은 평가 세트가 있습니다.

    꼭 알아 둘 것커널을 누가, 얼마나 큰 단위로 쓰느냐가 바뀌고 있습니다. 사람이 스레드 단위로 쓰던 커널을, 컴파일러와 AI가 더 큰 단위로 쓰는 쪽으로 옮겨 갑니다.
    PART 2

    Thread (스레드)

    여기까지가 커널이었습니다. 이제 커널을 실제로 실행하는 가장 작은 단위, 스레드로 넘어가겠습니다.

    2.1

    정의

    는 커널 코드를 실행하는 가장 작은 단위입니다.

    • 보통 데이터 하나에 스레드 하나를 맞춥니다. 오늘 예시에서는 스레드 하나가 숫자 하나에 2를 곱합니다.
    • 스레드마다 자기 번호와, 자기만 쓰는 저장 공간인 레지스터를 가집니다.
    • 스레드는 자기 번호를 보고 몇 번째 숫자를 맡을지 스스로 계산합니다.
    Q. 스레드 수와 CUDA Core 수는 같은가요?

    아닙니다. H100 SXM의 CUDA Core는 16,896개지만, 동시에 올라가는 스레드는 약 27만 개입니다. 스레드가 코어보다 훨씬 많아야, 메모리를 기다리는 스레드 대신 다른 스레드를 실행해 코어를 쉬지 않게 할 수 있습니다. 2회차에서 본 지연 은닉입니다.

    2.2

    등장 배경

    • 숫자마다 같은 계산을 하는 일은, 숫자마다 실행 흐름을 하나씩 두면 가장 쉽게 표현됩니다.
    • CPU에도 스레드가 있습니다. 그런데 CPU 스레드는 운영체제가 관리해서, 만들고 바꾸는 데 마이크로초 단위 시간이 걸립니다.
    • 수만 개를 만들면 관리하는 시간이 계산하는 시간보다 커집니다.
    "그럼 하드웨어가 직접 관리하는 아주 가벼운 스레드를 수십만 개 두자!" 그래서 2006년 G80과 CUDA에서 등장한 것이 바로 GPU 스레드입니다.
    • 스레드마다 레지스터를 미리 나눠 줘서, 만들고 바꾸는 비용이 거의 없습니다.
    • G80은 SM 하나에 스레드 768개, 칩 전체로 1만 2천여 개를 동시에 올렸습니다. H100 SXM은 약 27만 개입니다.
    2.3

    구조

    스레드 하나는 자기 번호와 자기 저장 공간을 가집니다.

    구성하는 일한계 (H100)
    threadIdx블록 안에서 내 위치 (x, y, z)블록당 최대 1,024
    스레드 전용, 가장 빠른 저장 공간스레드당 최대 255개
    레지스터가 모자랄 때 넘치는 공간실제 위치는 VRAM

    전체에서 몇 번째 스레드인지는 블록 번호, 블록 크기, 블록 안 번호로 계산합니다. 2.4에서 봅니다.

    Q. 기초 · 로컬 메모리는 이름이 "로컬"인데 왜 느린가요?

    스레드 하나만 쓰는 공간이라 로컬이라고 부를 뿐, 실제 위치는 VRAM입니다. 그래서 레지스터보다 훨씬 느립니다. 2회차 4.7에서 본 이 바로 이 공간으로 넘어가는 것입니다.

    2.4

    작동 방식

    1. 내 번호 계산하기

    숫자 100만 개를 256개씩 끊으면, 블록마다 맡는 구간이 이렇게 정해집니다.

    블록 번호맡는 숫자
    00번 ~ 255번
    1256번 ~ 511번
    2512번 ~ 767번
    ……
    3,906 (마지막)999,936번 ~ 1,000,191번 (999,999번까지만 실제 데이터)

    스레드는 세 값을 보고 자기 숫자를 찾습니다.

    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 전체에서 몇 번째 스레드인지
if (i < n) out[i] = in[i] * 2;                   // 범위를 벗어나면 아무것도 안 함
    1. 블록 번호: blockIdx.x는 내가 몇 번째 블록인지입니다.
    2. 블록 크기: blockDim.x는 블록 하나에 스레드가 몇 개인지입니다. 예시에서는 256입니다.
    3. 블록 안 번호: threadIdx.x는 블록 안에서 몇 번째인지입니다.
    4. 전체 번호: 블록 번호 곱하기 블록 크기, 더하기 블록 안 번호입니다. 2번 블록의 5번 스레드라면, 2 곱하기 256 더하기 5, 517번 숫자를 맡습니다.

    2. 범위 확인

    • 스레드는 블록 크기 단위로 만들어집니다. 데이터 수가 나눠떨어지지 않으면 마지막 블록에 남는 스레드가 생깁니다.
    • 오늘 예시에서는 마지막 블록의 스레드 192개가 남습니다.
    • 그래서 if (i < n)으로, 범위를 벗어난 스레드가 메모리를 건드리지 않게 막습니다.
    Q. 남는 스레드 192개는 어떻게 나왔나요?

    블록 3,907개 곱하기 256은 스레드 1,000,192개입니다. 숫자는 100만 개라서 192개가 남습니다. 이 192개가 범위 확인에 걸려 아무것도 하지 않습니다.

    3. 데이터가 스레드보다 많을 때

    스레드 하나가 여러 숫자를 차례로 맡습니다. 이걸 grid-stride loop라고 합니다. 4.8에서 봅니다.

    2.5

    이점

    • 매우 가볍습니다: 레지스터가 미리 나눠져 있어서 만들고 바꾸는 비용이 거의 없습니다.
    • 아주 많이 올라갑니다: H100 SXM은 SM 132개에 2,048개씩, 약 27만 개가 동시에 올라갑니다.
    • 코드가 단순합니다: 숫자 하나에 대한 처리만 적으면 됩니다.
    2.6

    부재 시 문제

    개별 스레드라는 단위가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 숫자 여러 개를 한 명령으로 처리하는 벡터 명령, 즉 SIMD를 직접 다뤄야 합니다. CPU의 AVX 코드를 손으로 쓰는 것과 비슷해서 난이도가 크게 오릅니다.
    • 숫자마다 다른 길을 가는 코드, 예를 들어 if문을 표현하기 어렵습니다.
    2.7

    단점

    • 하나하나는 느립니다: CPU 코어보다 클럭이 낮고, 다음 명령을 미리 짐작하는 분기 예측 같은 장치가 없습니다. 많이 써야 빠릅니다.
    • 혼자 움직이지 않습니다: 항상 32개, 즉 warp 단위로 함께 실행됩니다. PART 5에서 봅니다.
    • 레지스터를 많이 쓰면 덜 올라갑니다: 2회차 4.4에서 본 점유율 계산이 바로 이 부분입니다.
    • 같은 곳에 쓰면 충돌합니다: 여러 스레드가 같은 메모리 위치에 동시에 쓰면 결과가 꼬입니다. 이걸 , 영어로 race condition이라고 합니다.
    Q. 경쟁 상태는 실제로 어떻게 생기나요?

    스레드 여러 개가 합계 변수 하나에 1씩 더한다고 해 보겠습니다. 더하기는 "읽고, 더하고, 쓰기" 세 단계입니다. 두 스레드가 같은 값을 동시에 읽고 각자 1을 더해 쓰면, 2가 늘어야 할 것이 1만 늡니다. 그래서 결과가 기대보다 작게 나오고, 실행할 때마다 값이 달라집니다.

    sequenceDiagram
  participant A as 스레드 A
  participant M as 합계 변수 (지금 10)
  participant B as 스레드 B
  A->>M: 읽기, 10
  B->>M: 읽기, 10
  A->>M: 10 + 1 = 11 쓰기
  B->>M: 10 + 1 = 11 쓰기
  Note over M: 12가 되어야 하는데 11
    2.8

    단점 극복을 위한 대안 기술

    1. Atomic 연산

    • 뜻: 은 읽고 더하고 쓰는 세 단계를, 다른 스레드가 끼어들 수 없게 한 번에 처리하는 명령입니다. atomicAdd가 대표입니다. atomic은 "더 쪼갤 수 없는"이라는 뜻입니다.
    • 해결하는 단점: 경쟁 상태를 막습니다.

    2. warp 단위 합계

    • 뜻: 같은 warp 안의 스레드 32개가 먼저 자기들끼리 값을 합칩니다. 그다음 합계 하나만 atomic 연산으로 더합니다. 5.4에서 봅니다.
    • 해결하는 단점: atomic 연산 횟수를 32분의 1로 줄여서, 충돌로 기다리는 시간을 줄입니다.

    3. ILP

    • 뜻: , 우리말로 명령 수준 병렬성입니다. 2회차 4.8에서 본 기법으로, 스레드 하나가 서로 상관없는 계산 여러 개를 이어서 처리합니다.
    • 해결하는 단점: 레지스터를 많이 써서 스레드가 적게 올라가도 기다림을 숨깁니다.

    4. 타일 단위 도구

    • 뜻: Triton, cuTile Python처럼 개별 스레드를 감추고 타일 단위로 씁니다.
    • 해결하는 단점: 번호 계산과 범위 확인에서 생기는 실수를 줄입니다.

    최신 트렌드

    1. 스레드를 감추는 프로그래밍

    • cuTile Python과 Triton은 스레드 번호를 코드에 드러내지 않습니다. 개발자는 타일만 다루고, 스레드 배치는 컴파일러가 정합니다.
    • 2.4에서 본 번호 계산과 범위 확인을 직접 쓸 일이 줄어듭니다.

    2. Python으로 쓰는 고성능 커널: CuTe DSL

    • CUTLASS는 NVIDIA가 만든 행렬 곱셈 코드 모음입니다. CuTe DSL은 이걸 Python으로 쓰게 한 도구입니다.
    • FlashAttention-4가 이걸로 쓰였고, 기존 C++ 방식보다 컴파일이 20에서 30배 빠르다고 보고했습니다.

    3. 최고 성능 커널은 여전히 직접 다룹니다

    • FlashAttention-3, 4 같은 커널은 스레드와 warp 수준까지 직접 제어합니다.
    • 데이터센터용 Blackwell에서는 스레드 하나가 Tensor Core에 행렬 곱셈 명령을 냅니다. 스레드 하나의 역할이 커진 셈입니다. PART 5에서 봅니다.
    꼭 알아 둘 것생산성은 스레드를 감추는 타일 방식으로, 마지막 성능은 스레드를 직접 다루는 코드로 얻는 구도입니다.
    PART 3

    Block (스레드 블록)

    여기까지가 스레드 하나였습니다. 이제 스레드를 묶은 단위, 블록을 보겠습니다. 2회차에서 블록이 SM 하나에 배정된다는 것까지 봤습니다.

    3.1

    정의

    은 같은 SM에서 함께 실행되는 스레드 묶음입니다.

    • 스레드를 최대 1,024개까지 묶습니다. 오늘 예시에서는 256개씩 묶어 블록이 3,907개입니다.
    • 같은 블록의 스레드끼리만 Shared Memory를 함께 쓰고, 서로 기다려 줄 수 있습니다.
    • 블록끼리는 서로 독립입니다. 서로의 존재를 모른다고 생각하면 됩니다.
    • 공식 문서에서는 CTA, 즉 Cooperative Thread Array라고도 부릅니다.
    3.2

    등장 배경

    • 스레드끼리 협력해야 하는 일이 많습니다. 데이터를 함께 불러와 여러 번 다시 쓰면, 느린 VRAM을 덜 읽기 때문입니다.
    • 그런데 모든 스레드가 서로 협력하게 하면, 수십만 개를 한꺼번에 맞춰야 합니다. 그러면 SM 수가 다른 GPU마다 코드를 맞춰야 합니다.
    "그럼 가까운 스레드끼리만 묶어서 협력하게 하고, 묶음끼리는 서로 모르게 하자!" 그래서 2006년 CUDA와 함께 등장한 것이 바로 블록입니다.
    • 블록 안에서는 협력하고, 블록끼리는 독립이라 어떤 GPU에서든 나눠 실행할 수 있습니다.
    • 처음 G80에서는 블록당 스레드가 최대 512개였고, 2010년 Fermi부터 1,024개가 됐습니다.
    3.3

    구조

    블록 하나는 자기 번호, 크기, 함께 쓰는 공간, 함께 기다리는 장치를 가집니다.

    구성하는 일한계 (H100)
    blockIdx그리드 안에서 블록의 위치1차원에서 3차원까지
    blockDim블록 크기최대 1,024 스레드 (z축은 최대 64)
    블록 스레드끼리 데이터 공유기본 48KB, 설정하면 최대 227KB
    동기화 배리어__syncthreads()로 모두 도착할 때까지 대기블록 안에서만
    • 레지스터는 스레드마다 따로, Shared Memory는 블록이 함께 씁니다.
    • H100부터는 블록 여러 개를 다시 묶은 Thread Block Cluster도 있습니다. 3.8에서 봅니다.
    Q. 왜 Shared Memory는 기본 48KB이고, 따로 설정해야 227KB까지 쓰나요?

    예전 GPU와 맞추려고 기본 한도를 48KB로 두었습니다. 그보다 많이 쓰려면 커널마다 cudaFuncSetAttribute로 직접 허락해야 합니다. SM 전체의 228KB 중 1KB는 시스템이 쓰기 때문에, 블록 하나는 최대 227KB입니다.

    3.4

    작동 방식

    1. 실행 순서

    1. 배정: 커널이 시작되면 블록이 대기열에 오르고, 자원이 남는 SM에 하나씩 배정됩니다.
    2. warp로 나누기: 블록은 SM 안에서 32개씩 warp로 나뉩니다. 스레드 256개짜리 블록은 warp 8개입니다.
    3. 협력: 블록 안의 스레드는 Shared Memory로 데이터를 나누고, __syncthreads()로 서로 기다립니다.
    4. 끝: 블록이 끝나면 그 자리에 다음 블록이 들어옵니다. 블록끼리의 실행 순서는 정해져 있지 않습니다.

    2회차 1.4에서 본 실행 순서가 바로 이것입니다.

    2. 협력하는 코드

    __shared__ float tile[256];          // 블록이 함께 쓰는 공간
tile[threadIdx.x] = in[i];           // 각자 하나씩 불러오고
__syncthreads();                     // 모두 불러올 때까지 기다린 뒤
float v = tile[255 - threadIdx.x];   // 다른 스레드가 불러온 값을 씀
    1. 불러오기: 스레드마다 VRAM에서 숫자 하나씩 불러와 Shared Memory에 둡니다.
    2. 기다리기: 블록의 모든 스레드가 다 불러올 때까지 기다립니다.
    3. 함께 쓰기: 다른 스레드가 불러온 값을, VRAM을 다시 읽지 않고 씁니다.
    Q. __syncthreads()를 빼면 어떻게 되나요?

    다른 스레드가 아직 값을 넣지 않은 칸을 읽을 수 있습니다. 실행할 때마다 결과가 달라지는, 찾기 어려운 버그가 됩니다.

    3.5

    이점

    • 데이터를 다시 씁니다: VRAM 대신 Shared Memory에서 여러 번 읽습니다. 행렬 곱셈에서 블록 하나가 128 곱하기 128 조각을 맡으면, 불러온 값을 수십 번 다시 씁니다.
    • GPU 크기에 맞춰 저절로 늘어납니다: 블록이 서로 독립이라, SM 24개 GPU든 132개 GPU든 같은 코드가 블록을 나눠 실행합니다.
    • 자원 관리가 쉽습니다: 레지스터와 Shared Memory를 블록 단위로 잡고 풉니다.
    3.6

    부재 시 문제

    블록이라는 단위가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 스레드끼리 데이터를 나눌 방법이 VRAM뿐이라, 메모리를 오가는 시간이 병목이 됩니다.
    • 반대로 모든 스레드가 서로 기다릴 수 있게 하면, SM 수가 다른 GPU마다 같은 코드를 그대로 쓸 수 없습니다.
    3.7

    단점

    • 블록끼리는 직접 주고받을 수 없습니다: 필요하면 커널을 나누거나 atomic 연산을 써야 합니다.
    • 크기를 잘 골라야 합니다: 너무 작으면 SM을 못 채우고, 너무 크면 자원이 모자라 SM에 블록이 적게 올라갑니다.
    • 한도가 있습니다: 스레드 1,024개, Shared Memory 227KB를 넘을 수 없습니다.
    Q. 블록끼리는 왜 기다리지 못하게 했나요?

    블록 A가 블록 B를 기다리는데, B가 아직 SM에 올라오지 못했다고 해 보겠습니다. A는 SM 자리를 차지한 채 계속 기다리고, B는 자리가 나지 않아 올라오지 못합니다. 이걸 라고 합니다. SM이 적은 GPU일수록 잘 생기니, 블록을 독립으로 두어야 어떤 GPU에서든 같은 코드가 돕니다.

    3.8

    단점 극복을 위한 대안 기술

    1. Thread Block Cluster (H100부터)

    • 뜻: 2회차 1.8에서 본 입니다. 블록을 보통 최대 8개까지 묶어, 서로의 Shared Memory를 직접 읽게 합니다. 이렇게 여러 블록에 나뉜 Shared Memory를 하나처럼 쓰는 공간을 Distributed Shared Memory라고 부릅니다.
    • 해결하는 단점: 블록끼리 데이터를 나눌 때 VRAM까지 가지 않아도 됩니다.

    2. Cooperative Groups

    • 뜻: 는 스레드를 원하는 크기로 묶어 함께 기다리게 하는 기능입니다. 그리드 전체를 한 번에 기다리게 하는 grid.sync()도 있습니다.
    • 해결하는 단점: 블록끼리 맞춰야 할 때 커널을 나누지 않아도 됩니다. 단, 3.7의 교착 상태를 피하려면 모든 블록이 동시에 SM에 올라갈 수 있을 만큼만 띄워야 합니다.

    3. 블록 크기 추천 함수

    • 뜻: cudaOccupancyMaxPotentialBlockSize()는 커널의 자원 사용량을 보고 점유율이 가장 높은 블록 크기를 추천합니다.
    • 해결하는 단점: 블록 크기를 감으로 고르는 문제를 줄입니다.
    3.9

    3.10

    최신 트렌드

    1. Cluster가 본격적으로 쓰입니다

    • CUTLASS 3과 4, FlashAttention-3 같은 H100 이후 커널이 Cluster를 씁니다.
    • 같은 데이터를 VRAM에서 한 번만 읽어, Cluster 안의 여러 SM에 동시에 나눠 줍니다. 이 기능을 multicast라고 합니다.
    • VRAM에서 같은 데이터를 여러 번 읽지 않아도 됩니다.

    2. 두 SM이 행렬 곱셈 하나를 함께 합니다

    • 데이터센터용 Blackwell은 같은 Cluster 안의 블록 두 개가 짝을 이뤄, 큰 행렬 곱셈 하나를 함께 합니다. 이걸 2-CTA MMA라고 부릅니다. CTA는 3.1에서 본 블록의 다른 이름입니다.
    • 한 번에 맡을 수 있는 조각이 커져서 Shared Memory를 오가는 일이 줄어듭니다.
    • FlashAttention-4는 이 방식으로, 학습의 역전파 계산에서 atomic 연산을 절반으로 줄였습니다.

    3. 블록 단위 프로그래밍이 다시 주목받습니다

    • CUDA Tile은 블록 하나를 프로그래밍 단위로 삼습니다. 블록 안의 스레드 배치는 컴파일러가 정합니다.
    • 1.10에서 본 흐름과 같습니다. 개발자가 생각하는 단위가 스레드에서 블록으로 옮겨 갑니다.
    꼭 알아 둘 것블록끼리 독립이라는 원칙은 그대로지만, 가까운 블록끼리 협력하는 범위는 세대마다 넓어지고 있습니다.
    PART 4

    Grid (그리드)

    여기까지가 블록이었습니다. 이제 커널 한 번 실행으로 만들어지는 블록 전체, 그리드를 보겠습니다.

    4.1

    정의

    는 커널 한 번 실행으로 만들어지는 블록 전체입니다.

    • 커널을 한 번 실행하면 그리드가 하나 만들어집니다. 오늘 예시의 그리드는 블록 3,907개입니다.
    • 블록을 1차원에서 3차원까지 배치할 수 있습니다.
    • 데이터 크기에 맞춰 블록을 몇 개 만들지 정하는 가장 바깥 단위입니다.
    4.2

    등장 배경

    • 데이터 크기는 GPU와 상관없이 정해집니다. 숫자 100만 개는 GPU가 바뀌어도 100만 개입니다.
    • 일을 몇 조각으로 나눌지를 SM 수에 맞춰 정하면, GPU가 바뀔 때마다 코드를 고쳐야 합니다.
    "그럼 데이터 크기만 보고 조각 수를 정하고, 어느 SM에 줄지는 하드웨어에 맡기자!" 그래서 2006년 CUDA와 함께 등장한 것이 바로 그리드입니다.
    • 프로그래머는 블록 수만 정하고, 배정은 GigaThread Engine이 맡습니다.
    • 처음에는 2차원까지였고, 2010년 Fermi부터 3차원 그리드를 쓸 수 있게 됐습니다.
    4.3

    구조

    1. 1차원 그리드

    오늘 예시처럼 숫자가 한 줄로 늘어선 데이터는, 블록도 한 줄로 늘어놓습니다.

    구성뜻한계 (H100)
    gridDim그리드 크기, 즉 블록 수x축 최대 2³¹−1 (약 21억), y축과 z축 최대 65,535
    blockIdx그리드 안에서 블록의 위치-
    Q. 기초 · 블록 수를 왜 (n + 255) / 256처럼 쓰나요?

    올림 나눗셈입니다. 100만을 256으로 나누면 3,906.25입니다. 몫만 쓰면 블록이 3,906개라서 숫자 64개가 빠집니다. 255를 더한 뒤 나누면 3,907이 나와서 모든 숫자를 덮습니다.

    2. 2차원 그리드

    이미지나 행렬처럼 가로세로가 있는 데이터는 2차원 그리드로 짜면 번호 계산이 쉽습니다. 1920 곱하기 1080 이미지를 16 곱하기 16 조각으로 나누면, 가로 120개, 세로 68개 블록이 됩니다.

    dim3 block(16, 16);                               // 블록 하나 = 16 x 16 = 256 스레드
dim3 grid((1920 + 15) / 16, (1080 + 15) / 16);    // 120 x 68 블록
brighten<<<grid, block>>>(img);
    4.4

    작동 방식

    블록 3,907개가 한꺼번에 SM에 올라가지는 않습니다. SM이 한 번에 받을 수 있는 만큼 채우고, 끝나면 다음 블록을 채웁니다. 이 한 차례를 라고 합니다. 2회차 4.8에서 본 wave입니다.

    1. 한 번에 올라가는 블록 수: SM 수 곱하기 SM당 블록 수입니다. H100 SXM에서 256 스레드 블록이 SM마다 8개 올라가면, 132 곱하기 8, 1,056개입니다.
    2. 필요한 블록 수: 숫자 100만 개를 256개씩 나누면 블록 3,907개입니다.
    3. wave 수: 3,907 나누기 1,056, 약 3.7 wave입니다.
    4. 마지막 wave: 네 번째 wave에는 블록이 739개뿐이라 약 70%만 찹니다. 나머지 SM은 놉니다.
    Q. 기초 · SM마다 블록이 8개 올라간다는 건 어떻게 나왔나요?

    2회차 4.3에서 본 계산입니다. 256 스레드 블록은 warp 8개이고, SM의 warp 자리는 64칸이라 64 나누기 8, 블록 8개입니다. 레지스터와 Shared Memory는 넉넉하다고 가정한 예시입니다.

    Q. 그리드를 크게 잡으면 무조건 좋나요?

    GPU를 채우려면 충분히 커야 합니다. 하지만 너무 잘게 쪼개면 블록마다 반복되는 준비 작업이 늘어납니다. 그래서 4.8의 grid-stride loop처럼 블록 수를 SM 수의 몇 배로 고정하는 방식도 많이 씁니다.

    4.5

    이점

    • 데이터 크기만 보면 됩니다: 블록 수만 정하면 하드웨어가 SM에 나눠 줍니다.
    • 큰 GPU에서 저절로 빨라집니다: 같은 그리드라도 SM이 많으면 wave 수가 줄어듭니다. 오늘 예시는 RTX 4060에서 약 27 wave, H100 SXM에서 약 3.7 wave입니다. RTX 4060은 SM이 24개이고, SM 하나에 이 블록이 6개까지 올라가서 한 번에 144개씩 처리합니다.
    4.6

    부재 시 문제

    그리드라는 단위가 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 일을 SM 수에 맞춰 직접 나눠야 해서, GPU가 바뀔 때마다 코드를 고쳐야 합니다.
    • 데이터 크기와 하드웨어 크기가 한 코드에 섞여 관리하기 어렵습니다.
    4.7

    단점

    • 마지막 wave가 비면 손해입니다: 이걸 wave quantization, 우리말로 라고 합니다. 1.05 wave면 거의 2 wave만큼 시간이 걸립니다. 2회차 4.8의 "SM 132개에 블록 133개" 그림과 같은 이야기입니다.
    • 블록이 적으면 GPU 일부만 씁니다: 블록이 64개뿐이면 SM 132개 중 68개는 일을 받지 못합니다.
    • 그리드 전체가 서로 기다릴 수 없습니다: 3.7에서 본 이유로, 기본적으로는 커널을 나눠야 합니다.
    4.8

    단점 극복을 위한 대안 기술

    1. Grid-stride loop

    • 뜻: 는 블록 수를 SM 수의 몇 배로 고정하고, 스레드 하나가 여러 숫자를 반복해서 맡는 방식입니다.
    • 예시: 블록을 1,056개만 띄우면 스레드는 약 27만 개입니다. 숫자 100만 개를 맡으려면 스레드 하나가 숫자를 3에서 4개씩 차례로 처리합니다.
    • 해결하는 단점: 데이터가 커져도 블록 수가 고정돼서, 꼬리 효과가 줄어듭니다.
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
    out[i] = in[i] * 2;   // 그리드 전체 스레드 수만큼 건너뛰며 반복

    2. Persistent Kernel

    • 뜻: 1.8에서 본 방식입니다. 블록을 SM 수만큼만 띄워 두고, 대기열에서 일을 계속 가져옵니다.
    • 해결하는 단점: 꼬리 효과와 실행 비용을 거의 없앱니다. 대신 구현이 어렵습니다.

    3. Stream-K, Split-K

    • 뜻: 행렬 곱셈의 일을 SM 수에 맞게 잘게 나눠, 모든 SM이 거의 같이 끝나게 합니다.
    • 해결하는 단점: 행렬 곱셈의 꼬리 효과를 줄입니다.

    4. grid.sync()

    • 뜻: 3.8에서 본 Cooperative Groups 기능입니다. 그리드 전체를 한 번에 기다리게 합니다.
    • 해결하는 단점: 그리드 전체를 맞추려고 커널을 나누지 않아도 됩니다.
    4.9

    대안과의 비교

    블록을 몇 개 띄우느냐에 따라 꼬리 효과와 구현 난이도가 달라집니다.

    방식블록 수꼬리 효과특징
    원소당 스레드 (기본)데이터에 비례있음가장 단순
    Grid-stride loop고정 (SM 수의 몇 배)줄어듦데이터 크기와 상관없이 재사용

    4.10

    최신 트렌드

    1. 하드웨어가 일을 나눠 줍니다: Cluster Launch Control

    • 데이터센터용 Blackwell은 Cluster Launch Control, 줄여서 를 지원합니다.
    • 먼저 올라간 블록이, 아직 시작하지 않은 블록의 일을 가져가서 대신 처리합니다. 일을 넘긴 블록은 실행되지 않습니다.
    • 다른 커널이 SM 일부를 쓰고 있어도 일이 고르게 나뉩니다. 4.8에서 본 Persistent Kernel을 하드웨어가 돕는 셈입니다.

    2. 들쭉날쭉한 입력이 과제입니다

    • LLM 추론은 요청마다 입력 길이가 달라서, 그리드 크기가 SM 수와 잘 맞지 않는 경우가 많습니다.
    • 그래서 Stream-K나 Persistent Kernel처럼 블록 수를 SM 수에 맞추는 방식이 널리 쓰입니다.

    3. SM이 늘수록 꼬리 효과가 커집니다

    Rubin은 SM이 224개입니다. 한 wave에 들어가는 블록이 많아져서, 작은 작업일수록 GPU를 다 채우기 어렵습니다.

    꼭 알아 둘 것그리드는 "데이터 크기만큼 띄우는 것"에서 "SM 수만큼 띄우고 일을 나눠 주는 것"으로 바뀌고 있습니다.
    PART 5

    Warp (워프)

    여기까지 커널, 스레드, 블록, 그리드를 봤습니다. 넷은 프로그래머가 정하는 단위였습니다. 마지막으로 하드웨어가 정하는 실행 단위, warp를 보겠습니다. 2회차에서 warp를 짧게 봤다면, 오늘은 warp가 성능에 주는 영향을 봅니다.

    5.1

    정의

    는 하드웨어가 실제로 한꺼번에 실행하는 스레드 32개 묶음입니다.

    • 32개 스레드가 같은 명령을 각자 다른 데이터에 동시에 실행합니다. 오늘 예시라면 숫자 32개에 "2를 곱하라"는 명령 하나가 동시에 실행됩니다.
    • 이 방식을 SIMT, 즉 명령 하나에 스레드 여러 개라고 부릅니다.
    • 프로그래머가 만들지 않습니다. 하드웨어가 블록을 32개씩 자동으로 나눕니다.
    • 이름은 베틀에 나란히 걸린 날실, 영어로 warp에서 왔습니다. 실이라는 뜻의 thread와 짝을 이루는 말입니다.
    5.2

    등장 배경

    • 스레드마다 명령을 따로 읽고 해석하면, 명령을 다루는 회로가 계산 회로보다 커집니다.
    • 그래픽에서는 이웃한 픽셀들이 거의 같은 계산을 했습니다. 명령을 함께 써도 손해가 적었습니다.
    "그럼 32개 스레드가 명령 하나를 함께 쓰게 하자!" 그래서 2006년 G80에서 처음 등장한 것이 바로 warp입니다.
    • 명령을 읽는 비용을 32개가 나눠 내서, 아낀 면적에 계산 유닛을 더 넣었습니다.
    • 프로그래머에게는 스레드 하나하나로 보이고, 하드웨어는 묶음으로 처리합니다.
    • 32라는 크기는 G80부터 지금까지 그대로입니다. 이유는 2회차 1.4에서 봤습니다.
    5.3

    구조

    블록은 블록 안 번호 순서대로 32개씩 잘려 warp가 됩니다. 오늘 예시의 256 스레드 블록은 warp 8개입니다.

    구성뜻H100 기준

    warp 안에서의 자리 번호0부터 31

    Q. 기초 · 내가 몇 번 warp의 몇 번 lane인지는 어떻게 구하나요?

    블록 안 번호인 threadIdx.x를 32로 나눈 몫이 warp 번호이고, 나머지가 lane 번호입니다. 예를 들어 70번 스레드는 2번 warp의 6번 lane입니다.

    5.4

    작동 방식

    warp가 성능에 주는 영향은 세 가지 장면에서 드러납니다. 길이 갈릴 때, 메모리를 읽을 때, 값을 주고받을 때입니다.

    1. 분기 (Divergence)

    2회차 1.7에서 본 , 즉 같은 warp의 스레드가 if문에서 서로 다른 길로 가는 것을 코드로 보면 이렇습니다.

    if (threadIdx.x % 2 == 0) A(); else B();         // 나쁨: 같은 warp 안에서 갈림. A와 B를 차례로 실행
if ((threadIdx.x / 32) % 2 == 0) A(); else B();  // 좋음: warp 단위로 갈림. 손해 없음
    • 첫 줄은 같은 warp 안에서 짝수와 홀수가 갈립니다. A와 B를 차례로 실행해서 시간이 두 배 걸립니다.
    • 둘째 줄은 warp 단위로 갈립니다. 어떤 warp는 A만, 다른 warp는 B만 실행해서 손해가 없습니다.

    2. 메모리 병합 (Coalescing)

    • warp의 32개 스레드가 이웃한 주소를 읽으면, 하드웨어가 읽기를 몇 번으로 합칩니다. 이걸 이라고 합니다.
    • 예를 들어 4바이트 숫자 32개, 모두 128바이트를 32바이트 묶음 네 번으로 읽습니다.
    • 주소가 흩어져 있으면 묶음을 따로따로 읽어서 최대 32번까지 늘어납니다.
    • 오늘 예시는 스레드 0번이 숫자 0번, 1번이 1번을 읽으니 이웃한 주소입니다. 병합이 잘 되는 좋은 경우입니다.

    3. warp 안에서 값 주고받기 (Shuffle)

    • __shfl_down_sync로 Shared Memory를 거치지 않고 다른 lane의 레지스터 값을 직접 받습니다. 이걸 이라고 합니다.
    • 32개 값의 합계를 다섯 번 만에 구합니다. 16칸, 8칸, 4칸, 2칸, 1칸 떨어진 값을 차례로 받아 더합니다.
    Q. Volta부터 생긴 독립 스레드 스케줄링은 무엇이 바뀌었나요?

    스레드마다 다음 명령 위치, 즉 프로그램 카운터를 따로 두게 됐습니다. 그래서 분기 중에도 스레드끼리 서로를 기다리는 코드가 멈추지 않습니다. 다만 분기의 시간 손해는 그대로입니다. 갈린 길은 여전히 차례로 실행됩니다.

    5.5

    이점

    • 명령 회로를 아낍니다: 명령 해석을 32개가 함께 해서, 같은 면적에 계산 유닛을 더 넣습니다. 2회차에서 본 SM 하나에 CUDA Core 128개가 그 결과입니다.
    • 바꾸는 비용이 없습니다: warp마다 레지스터가 따로 있어서 매 사이클 다른 warp로 바꿀 수 있습니다. 2회차의 이 이 덕분입니다.
    • 메모리를 묶어 읽습니다: 이웃 주소를 읽으면 32번 읽을 것을 네 번으로 줄입니다.
    5.6

    부재 시 문제

    warp 같은 묶음이 없다고 가정해 보면, 이런 문제가 생깁니다.

    • 스레드마다 명령을 따로 처리해야 해서, CPU처럼 명령 회로가 커집니다.
    • 같은 칩 면적에 넣을 수 있는 계산 유닛이 크게 줄어듭니다.
    • 메모리를 스레드마다 따로 읽어서 대역폭을 많이 씁니다.
    5.7

    단점

    • 분기가 많으면 느립니다: 길이 갈릴 때마다 차례로 실행합니다.
    • 흩어진 주소는 느립니다: 데이터 배치가 나쁘면 대역폭을 낭비합니다.
    • 32의 배수가 아니면 빈칸이 생깁니다: 2회차 4.4에서 본 대로, 블록이 스레드 100개면 마지막 warp는 4칸만 일합니다.
    • 다른 회사 GPU로 옮길 때 문제가 됩니다: 32를 가정한 코드는, 64개가 한 묶음인 AMD 데이터센터 GPU에서 틀릴 수 있습니다.
    5.8

    단점 극복을 위한 대안 기술

    1. 분기 줄이기

    • 뜻: 데이터를 미리 정렬해 같은 warp가 같은 길을 가게 하거나, if문 대신 계산식을 씁니다.
    • 해결하는 단점: 분기로 생기는 시간 손해를 줄입니다.

    2. SoA 데이터 배치

    • 뜻: 점마다 x, y, z를 묶어 저장하지 않고, x끼리, y끼리, z끼리 모아 저장합니다. 앞의 방식을 AoS, 즉 구조체의 배열이라 하고, 뒤의 방식을 , 즉 배열의 구조체라고 합니다.
    • 해결하는 단점: 이웃한 스레드가 이웃한 주소를 읽게 돼서, 메모리 병합이 됩니다.
    저장 방식메모리에 놓이는 순서스레드들이 x만 읽을 때
    AoS (구조체의 배열)x0 y0 z0 x1 y1 z1 …주소가 띄엄띄엄, 병합 안 됨
    SoA (배열의 구조체)x0 x1 x2 … y0 y1 y2 …주소가 이웃, 병합 됨

    3. Warp Specialization

    • 뜻: 은 warp마다 역할을 나누는 방식입니다. 일부 warp는 데이터만 불러오고, 나머지 warp는 계산만 합니다. FlashAttention-3이 대표 예입니다.
    • 해결하는 단점: 데이터 불러오기와 계산을 겹쳐 기다림을 숨깁니다.

    4. warpSize 사용

    • 뜻: 32를 코드에 직접 쓰지 않고 내장 변수 warpSize를 씁니다.
    • 해결하는 단점: 묶음 크기가 다른 GPU로 옮길 때 생기는 문제를 줄입니다.

    5.10

    최신 트렌드

    1. Warp Specialization이 표준이 됐습니다

    • 5.8에서 본 Warp Specialization이 FlashAttention-3과 4, ThunderKittens, CUTLASS 같은 최신 고성능 커널의 기본 방식이 됐습니다.
    • FlashAttention-4는 B200에서 BF16 기준 최대 1,613 TFLOPS, 이론 성능의 약 71%를 냈다고 보고했습니다. cuDNN 9.13보다 최대 1.3배 빠릅니다.

    2. Tensor Core 명령을 스레드 하나가 냅니다

    • H100에서는 warp 4개, 즉 warpgroup이 함께 행렬 곱셈 명령을 냈습니다.
    • 데이터센터용 Blackwell에서는 스레드 하나가 tcgen05라는 명령을 냅니다. 결과는 2회차 1.10에서 본 Tensor Core 전용 저장 공간, 에 쌓입니다.
    • 결과를 레지스터에 두지 않아서 레지스터 부담이 줄고, warp마다 역할을 나누기가 더 쉬워졌습니다.
    • 게이밍용 RTX 5090에는 TMEM이 없어서 이 방식을 쓸 수 없습니다.

    3. warp를 감추는 흐름

    • cuTile, Triton 같은 타일 방식은 warp를 코드에서 감춥니다.
    • warp를 직접 다룰지, 컴파일러에 맡길지가 성능과 생산성 사이의 선택이 됐습니다.
    꼭 알아 둘 것최신 GPU에서 warp는 "같은 일을 하는 32개 묶음"에서 "역할을 나눠 맡는 단위"로 바뀌고 있습니다.
